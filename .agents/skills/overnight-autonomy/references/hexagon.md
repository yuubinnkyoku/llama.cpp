# Hexagon / llama.cpp：継続開発の共通規則

この資料は **Phase番号・特定コミット・その日の端末状態に依存しない恒久的な作業規則** です。進捗、測定値、次の開発課題は各Phaseの報告書とユーザーの最新 `/goal` に記録します。このSkillはPhaseが進んだだけでは更新しません。安全条件・作業原則に恒久的な変更があったときだけ更新します。

## 開始時：唯一の「現在地」を特定する
1. 最新のユーザー指示、`git status` / HEAD / branch / worktree / remote、未コミット差分を確認し、既存成果を壊さない。既知の過去の未コミットファイル数を固定的な事実として扱わず、その場で調べる。
2. `iq2s-device-test/phase20-autonomous-correctness-memory/continuations/` 以下の **最新の報告書・引き継ぎ・実測** を、現行ソースと照合する。過去の `hexagon-phase*.md` は履歴資料であり、現在地を保証しない。
3. 対象モデル・GGUF・量子化型・テンソル形状・機種/HTP世代・ビルドと配置ライブラリのハッシュ、NGL、分割設定、実機接続、安全ガードの状態を確認する。古い性能表・誤差値を現在の測定と混同しない。
4. 当該 `/goal` の **目標・合格条件・許可・禁止・測定条件** を短く固定する。新しい明示指示が優先。未指定の性能目標や根拠のない精度閾値を勝手に設定しない。

## 実装と数値正当性
- **独立したCPU参照と同一入力の対象バックエンド参照**を使う。CPU対DSPの結果は丸め・演算順序が異なり得るため、ビット一致を無条件に要求しない。重み形式・復号・境界・非有限値・センチネル・未書き込み・型と形状ゲートを検証する。
- 行分割など複合演算では、CPU担当部分は同一CPU参照、DSP/HTP担当部分は同一入力のフルHTP参照で比較する。新しい分割境界・形状・型は独立に検証する。未測定の区間を `nonbit=0` などと報告しない。
- BF16など型変換の厳密性と、その後の積和の誤差は**別々**に検証する。`FLOAT32` 宣言だけで内部演算精度を保証しない。単独演算・数ステップの再実行・可能なら長めの安定性・logits差分を区別する。
- 同一トークン列への条件付きlogits比較と自由生成の比較は別物。品質は可能なら固定した評価集合のNLL/perplexityやタスク評価で調べ、単独カーネルの正当性だけから品質同等と結論づけない。
- 速度を上げるために参照実装や既定の許容誤差を黙って変更しない。失敗を成功扱いする自動復旧を導入しない。小さな変更→局所検証→実モデル検証→記録→コミットで進める。

## 計測・判断
- **最終指標はモデル全体の処理時間**。カーネル単独のGB/s、ノード数、論理的な重みサイズ、転送量推定、DSP実行時間を混同しない。理論上限は仮説と明記し、差分を実測する。
- 同一モデル、入力トークン列、NGL、CPUスレッド数、端末状態、周波数上限/温度、画面・給電条件で対比較する。順序効果を減らす交互測定と複数組を使い、中央値・ばらつき・測定成立数を記録する。fast/throttled/Dozingを別系列として扱う。
- 周波数上限は開始・終了時に必ず記録し、可能なら試験中にも観測する。途中で変化したrunは同一条件の比較から除く。初回ステップを含む全体時間と定常ステップは分ける。外れ値除外の規則は先に決める。
- 非同期キューではホストの投入復帰、先行演算の同期待ち、転送、DSP内部の実行時間を分ける。未同期のDSP出力を読まない。計測の同時実行安全性・負担を検証し、未測定時間をゼロと書かない。
- **診断は競合を隠す。** ダンプ・待ち・ログを足すと、先行演算が回収されて不具合が消えることがある。診断あり・なしの両方を取り、片方だけで正常と判断しない。
- **同じ演算をCPUとDSPに分ける構成は、CPU側が他のアプリと資源を奪い合う。** 端末が使われている間の計測はCPU側に不利に偏る。比較は端末がidleな窓で行い、DSPだけの経路とCPUを噛ませる経路を同じ負荷条件で測る。

- HTPへ移すか否かは、**CPU側で削減できる時間−DSP側に増える時間−転送/待機等の増分**で判定する。特定の実効帯域目標やNGL、CPU比率を恒久的な合格条件にしない。速くない案は既定経路に昇格しない。
- 実際のDRAM転送量とグラフ上の重みサイズを混同しない。オフロード範囲、量子化型、共有メモリ、VTCM、キャッシュ整合性、バッファ所有権・寿命の差を確認する。

## 実機・安全・Git
- **少なくとも従来の安全ガードを維持**：1試験180秒以内、Swap-out増分1024 MiBで当該試験停止。DSP異常、OOM兆候、強い熱制限でも停止。新しい引き継ぎにより厳しいガードがあればそちらを適用する。ガードを勝手に緩めない。
- 温度保護・vendor電源ポリシー・ZRAM・重要サービスには介入しない。ADBがWi-Fi/TCPだけの場合、端末の再起動は禁止。端末設定を測定のために変更したら終了時に戻す。既知の安全な周辺アプリ停止以外の破壊的操作を避ける。
- 冷却や画面の制御で周波数上限が戻らない場合、電力ポリシー原因と断定せず、環境制約として記録する。権限外の操作で測定値を作らない。
- メインworktreeと未コミット差分を保護し、隔離worktree・専用ブランチを用いる。**push/merge/強制pushは、当該指示で明示的に許可されたもの以外禁止**。過去の検証済みコミットや比較基準を改変しない。
- 再試行に固定回数の上限はないが、新情報のない反復は禁止。実機で詰まればホスト側の解析・小さな再現試験・報告書整備に切り替える。端末再起動等の承認待ちを理由に、他の安全な作業まで止めない。

## 報告とSkillの更新方針
- 終了時は `PASS / PARTIAL / FAIL / BLOCKED` を目標ごとに分け、測定成立数・実測・正当性・未検証・安全ガード発動・差分・コミット・再現コマンド・次の一手を、**当該Phaseのcontinuations報告書**に残す。
- **Phase番号が増えたという理由でSkillを更新しない。** 実測値、カーネルの進捗、特定のHEAD、次の候補、日ごとの端末状態は報告書に置く。Skillを書き換えるのは、別のPhaseや作業にも使える**恒久的な規則が変わった場合のみ**。その場合も旧来の安全条件を保ち、変更理由を記録する。
