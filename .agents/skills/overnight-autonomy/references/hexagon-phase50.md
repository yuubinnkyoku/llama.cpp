# Hexagon / llama.cpp：Phase 50 の基準

Phase 49 で確定した数値と、Phase 50 で守る測定条件をまとめる。
規則の本体は `../SKILL.md` と `hexagon.md`。Phase 49 の作業契約は `hexagon-phase49.md`。
このファイルは Phase 50 以降の /goal で最初に読む。**旧 `hexagon.md` は Phase 48 時点の履歴資料であり、BF16未実装・CPU最速などの旧記述を Phase 50 の事実として扱わない。** 今回の明示指示と最新の実測・現行コードを優先する。

## 確定ベースライン（Phase 49、同一ビルド `533b03638`）

標準構成は **NGL=16 / `GGML_HEXAGON_SPLIT=0` / bf16 カーネル有効 / IQ3 gather 有効**。
CPU 側の比較対象は **NGL=0**（正規の CPU 経路）。NGL=24/32 は追加評価のみ。

熱制限下（cap 2112000 / 1862400、8 step、step 1-7 の中央値）:

| 構成 | ms/token |
|---|---:|
| CPU 単独 NGL=0 | 約 735 |
| NGL=9 SPLIT=0 | 約 660 |
| NGL=16 SPLIT=0 | 約 645 |

fast cap（cap 3628800 / 4608000）:

| 構成 | ms/token |
|---|---:|
| CPU 単独 NGL=0 | 467-482 |
| NGL=9 SPLIT=0 | 467-474 |
| NGL=16 SPLIT=0 | 476 |

fast cap は同等であり、性能 PASS ではない。**熱制限下のみ PASS**。
条件の違う数値を直接比べない。Phase 50 では同じ手順で取り直した数値を優先する。

DSP 実時間は 1 token あたり約 59 ms（IQ3 gather 最適化後）。CPU split は 394-401 ms（NGL=9、fast cap）。
CPU/DSP の重複量はグラフの分割構造で変わる。実際の重複・待機を計測せずに、単純加算や完全並列とみなさない。

## 周波数と画面状態（最重要）

- 画面 OFF（Dozing）では CPU が **883200 / 768000** に固定される。この状態の数値は測定に使わない。
- 画面 ON で fast cap 3628800 / 4608000。負荷が続くと温度制御が **2112000 / 1862400**、
  さらに **1785600 / 1497600** へ落とす。tier は 3 つ以上あるので、記録した値で系列を分ける。
- 充電していない端末では `svc power stayon true` は効かない。`input keyevent KEYCODE_WAKEUP` を
  20 秒ごとに送る以外に画面を保つ方法は確認できていない（2026-11-10 実測）。
  給電すると `stayon` が効く。
- **試験の前後で `scaling_max_freq` を記録し、変わった run は捨てる。** 開始時だけの記録では足りない。
  実際に 8 step の途中で 3628800 -> 2112000 へ落ちた例がある。
- DSP クロックは 2112 MHz 固定。熱制限で DSP が遅くなるとは書かない。
- **run を長くしてもばらつきは減らない。** 16 step 1 回は 714-2005 ms で外れ値が 1 回入り、
  中央値は 8 step の組と同じだった。ばらつきは step 数ではなく背景負荷で決まる。
  外れ値を除く規則を測る前に決め、8 step を 4 組以上取る。

## メモリ前提

- `run49.sh` の前提は MemAvailable 9500000 kB 以上、SwapFree 8000000 kB 以上、residency 95% 以上。
- 背景アプリが anon page を持つと、モデルの page cache を広げるために swap-out が増える。
  1024 MiB の swap-out ガードは**緩めない**。ガードに掛かった run は捨てて環境を整えてから取り直す。
- 実測（2026-11-10）: 背景アプリを止めないと NGL=0 の 1 run で 1073-1139 MiB の swap-out が出て
  ガードに掛かる。止めれば通る。Phase 50 でも試験前に止める。

## 測定手順（固定）

1. 背景アプリを止める（`am force-stop` の対象は下のスクリプトと同じ）。
2. 画面を起こし、cap が fast か throttled かを記録する。どちらの系列かは run ごとに記録する。
3. `GGML_SCHED_SPLIT_TIMING=1 GGML_SCHED_DEBUG=1` で 8 step 以上を回す。
4. ABBA で交互に最低 4 組。同じ cap の組だけを比較する。
5. step 0 を含む中央値と step 1-7 の中央値を両方出す。ばらつき（最小-最大）も出す。
6. 差が 5% 未満なら、その組では「差なし」と書く。1-2% の差を PASS にしない。
7. 試験は 1 回 180 秒以内。swap-out 1024 MiB、DSP 異常、OOM 兆候、強い熱制限で当該試験を停止。端末の温度保護・ZRAM・重要サービスを変更しない。性能の最終比較では診断計測の有無も揃え、計測による負担を記録する。

再現スクリプトは `iq2s-device-test/phase20-autonomous-correctness-memory/continuations/c49/` の
`p495_run.sh`（端末側ラッパー）と `p495_abba.sh`（交互比較）を使う。

## Phase 50 の合格条件（提案）

性能:

- fast cap で、同一条件の NGL=0 より NGL=16 が再現性をもって速いこと。目標は 5% 以上。
- 5% 未満しか出ない場合は、その時点のばらつきを測り、閾値を上げ下げするのではなく
  「未達」として記録する。熱制限下の優位（約 12%）を壊さないこと。

正当性:

- bf16 単独試験 PASS（65536 パターンのビット一致、M=1/2/3、K=5120/5152/96、非有限 0）。
- IQ3 単独試験 PASS（4 step logits が基準 `5585d4ed...` とバイト一致）。
- 2 / 4 / 16 step が exit 0、非有限 logits なし、CPU split の logits が基準 `577417e9...` と一致。
- 数値契約を緩めない。既存の 33 テンソル分割のビット一致を壊さない。

安全:

- メモリガード違反なし、DSP 異常なし、CPU 単独経路の回帰なし。

比較:

- 最適化の前後で同じモデル・NGL・cap・入力（同じ replay token 列）を使う。
- 変更前後の比較と CPU 単独との比較を両方残す。

## Phase 50 で優先する作業（Phase 49.5 の実測から）

1. **CPU 側で処理する重みを減らす。** NGL=0 のグラフに現れるテンソルの論理的な読み出し対象サイズは
   合計 8514 MiB、そのうち MUL_MAT の重みは 8183 MiB（497 本、96.1%）。これは**実DRAM転送量や実行時間の96.1%ではない**。
   NGL=16 の CPU 区間に全量を帰属させず、移動する層ごとにCPU削減時間とHTP追加時間を実測する。cap 1785600 では 1 層あたり CPU 22.8 ms 減 / DSP 8.1 ms 増で、
   **同じ 1 バイトを DSP の方が 2.5-2.8 倍効率よく処理する**。ここが最大の余地。
   IQ2_S（9.85 GB/s）/IQ2_XS（7.81 GB/s）の高速化を優先するが、**30 GB/sは参考目標で絶対的な移行条件ではない**。
   型・形状・NGLごとのCPU削減時間−HTP追加時間を測り、正味で得な層だけを移す。
2. **現在の2 split構成では大きなCPU/DSP重複を期待しない。** NGL=16 の計測例ではCPU約610 ms、
   DSP約130 ms、全体約740 msで重複は小さい。依存関係を確認しないまま同期を削ったり、
   他のNGL・分割構造にも重複ゼロを一般化したりしない。
3. **IQ2_S / IQ2_XS の gather 最適化**（B）。単独では 0.5% だが 1 の前提になる。
4. **32x2 の IQ3 実装**。prefill 専用。decode の改善として計上しない。
5. **キャッシュ dirty 区間と flush**。実費用が小さいなら後回し。整合性の別ゲートが要る。

## Phase 50 の実測で確定したこと（2026-11-10）

以下は実測。次の Phase はここから始めてよい。詳細は
`iq2s-device-test/phase20-autonomous-correctness-memory/continuations/c50/phase50-report.md`。

### IQ2 の gather は「先行発行」で伸びる（実施済み・既定に入った）

IQ2_S は 1 グループ分の 2 本の `vgather` を同じ scratch 対に落として直後に読んでいた。
グループごとにスロット対を持たせ、タイルの 8 本を先に出してから読む形にすると:

| 型 | 変更前 | 変更後 | DSP 時間 |
|---|---:|---:|---:|
| IQ2_S | 10.21 | 14.17 GB/s | -27.9% |
| IQ2_XS | 7.68 | 9.61 GB/s | -20.0% |
| IQ2_XXS | 6.92 | 8.57 GB/s | -19.2% |

IQ2_XS / IQ2_XXS は 1 グループ 4 本（grid 2 + sign 2）なので、2 グループずつ 2 パスに
分けて 8 本を飛ばす。**16 本を同時に生かすとレジスタが足りない。**
`IQ2S_SCRATCH_STRIDE` は 512 -> 1024。VTCM 予約 128 KiB のうち 44,288 -> 49,408 バイトで
まだ余裕がある。**この変更は logits をバイト一致させた**（NGL=9/16/24 のすべてで確認）。
IQ3_S / IQ3_XXS の帯域は 0.1% 以内で動かない。これが「条件が同じだった」証拠になる。

### IQ2_XS / IQ2_XXS の符号は算術で作れる（実施済み）

`ksigns64` は **7 bit インデックスの偶数パリティ展開**。バイト j (j<7) は
「bit j が立っていれば 0xff」、バイト 7 は「パリティが奇数なら 0xff」。
128 件すべて一致する（`p50_ksigns_check.py`）。したがって sign の 2 本の gather は
算術に置き換えられる。IQ2_S が使っている `iq2_s_sign_mask_arith()` を再利用し、
高い 4 バイト側は「bit 4-6 とパリティをバイトへ広げる」補助を足す。

1 グループの gather は 4 本 -> 2 本。IQ2_XS 9.61 -> 10.85 GB/s、
IQ2_XXS 8.57 -> 9.25 GB/s（2 run で再現）。IQ2_S と IQ3 系は 0.1% 以内で不動。
logits は `f3a0d235` でバイト一致。**全体効果は -0.12% しかない**が、
厳密に仕事が減る変更なので入れてよい。

### NGL は 16-24 で飽和する。増やすと遅くなる

throttled cap 2112/1862、8 step。**推定子は「run ごとの最小 step の run 間中央値」**。
中央値は停止で 28% 動くので使わない（同じ NGL=16 でも 686.1 と 880.6）。
最小 step なら同じ 2 run が 615.1 と 617.3 で 0.3% しか違わない。

| NGL | run 数 | 最小 step の中央値 ms | 対 CPU 単独 |
|---:|---:|---:|---:|
| 0 | 6 | 681.3 | - |
| 16 | 9 | 615.0 | -9.7% |
| 24 | 6 | 600.8 | -11.8% |
| 28 | 1 | 627.1 | -8.0% |
| 32 | - | swap-out ガードで停止 | 測定不可 |

**16 と 24 は 2% 級で、最小値の範囲が重なるため優劣を決められない。**
どちらも CPU 単独より 10-12% 速い。28 は 16 より遅い。

理由は型ごとの DSP/CPU 効率比。**IQ3_S 6.4x、IQ3_XXS 3.0x、IQ2_S 1.9x、
IQ2_XS 1.2x、IQ2_XXS 0.7x（CPU の方が速い）。**
最良の IQ3_S は層 48-63 に集中していて、そこは NGL=16 で既に DSP に載る。
**NGL を 16 より上げると IQ2_XXS のような CPU が得意な型を DSP へ移して損をする。**

### 順序効果に注意

回文順でない系列では後半の run が有利に出る。同じ NGL=0 で
g1 741.9 -> g3 700.3 (5.6%) の例がある。**必ず 0,16,24,24,16,0 のように
往復で取る。**

### CPU スレッドは 7 のまま。8 は 40% 遅い

NGL=16、8 step の中央値。6 スレッド 717-727 ms、**7 スレッド 632-716 ms**、
8 スレッド 940-952 ms。8 コア全部を CPU の積和で埋めると HTP の駆動側
（FastRPC のホストスレッド）が回らず、DSP に仕事が渡らない。
**「コアを全部使う」方向の変更をしない。**

### 選択的配置（層の途中に HTP テンソルを置く）は採用しない

`override` で層 36 の FFN 3 本（約 110 MiB）だけを HTP へ移す試験をした。
**split が 2 -> 4 に増えた。** 時間は改善しなかった（最小 step 639-681 ms に対し
無変更側 498-620 ms）。split 境界ごとに固定費が乗るため、110 MiB を移して得られる
数 ms を打ち消す。層は逐次依存なので、CPU 区間の中に 1 枚置くたびに 2 境界増える。
**層の上から N 枚という一律配置から離れない。**

### CPU/DSP の重複はこの 2 split 構成では作れない

NGL=16 のグラフは `splits = 2`（CPU が層 0-48、HTP が層 49-63）。CPU 区間 531 ms に対し
DSP 104 ms で、DSP は 84% 遊んでいる。しかし層が逐次依存なので、順序を変えても
重ならない。重複を作る唯一の道は 1 テンソル内の row split（Phase 46 の機構）で、
**34 テンソル目 `blk.63.attn_output.weight` の不具合原因が未解明のまま拡大しない**
という制約がまだ生きている。

### 測定環境の床（重要）

- **DSP 時間は `ggml-sched-split` から読めない。** `OPPOLL=0`（非同期投入）では
  CPU 側 587,123 us に対し HTP 側 342 us と出る。これは投入の戻りだけ。
  DSP 時間は `GGML_HEXAGON_PROFILE=1` の op 別 `usec` の合計を使う。
- **16 GB 端末ではメモリが常にぎりぎり。** NGL=16 で mmap 8.66 GB + HTP のタイル化
  コピー約 2.26 GB + 常駐アプリ 2.2 GB で、`MemFree` は 200 MB 前後。
  1 run あたり 400-840 MiB の swap-out が出て、**2-10 秒の停止が 1 run に 1-2 回**入る。
  アプリを止めても `AnonPages` は 1 GB 前後までしか減らない。
- その結果 **8 step の run 間ばらつきは ±8%**。1-2% の差は原理的に分解できない。
  1% 級の主張を run 全体の時間でしたいなら、部品（op 別 usec）で示すこと。
- 外れ値は中央値で捨てる。**中央値が動く停止だけを捨てる**と先に決めておく。

### vendor の CPU cap は一度張り付くと戻らない

2026-11-10 の実測。cap 2112000 / 1862400 に張り付いたあと:

- 冷却では戻らない。`tz0` を 26.9 C まで下げても同じ。
- 画面 SLEEP -> WAKEUP -> MENU、`svc power stayon true` でも戻らない。
- `system_server` の再起動（system pid が変わる、uptime は 4.1 日で継続）でも戻らない。
- Android の熱制御ではない。全 cooling_device が `cur_state 0`、`Thermal Status: 0`、
  hw trip は 105 C。Nubia の電力ポリシー。
- バッテリーセーバーは off、deviceidle は ACTIVE。
- **8 step の run の途中でも 3628800 -> 3513600 -> 3187200 と動く。** fast cap の窓は短い。
- ADB が TCP のみの間は再起動しない規約なので、**fast cap は取れないものとして扱う。**
  `cpuinfo_max_freq` は 3628800 (policy0, core 0-5) と 4608000 (policy6, core 6-7)。
  cpufreq policy は 2 個だけで、Phase 49 の資料にある policy0/4/7 は同じ 2 個への別名。

### 計器

- `p50_prof_bw.py` は profile の M=1 行だけを型別に集計する。Phase 49.5 の公表表
  （IQ3_S 28.10、IQ3_XXS 21.99、IQ2_XS 7.81、IQ4_XS 61.95、合計 35.21 GB/s）を
  再現してから使うこと。M=5 の prefill 行を混ぜると値が半分になる。
- `test-backend-ops perf` はこの backend では使えない。1 op が 121,638 us と出るが、
  それは重みのアップロードであってカーネルではない（実 run では 500-1500 us）。
- `p50_layer_types.py` で層ブロック×型の重み量が出る。合計 8183 MiB が Phase 49.5 と一致する。
