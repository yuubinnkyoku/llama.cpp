## B. IQ2 高速化

### 原因

IQ2_S の 32x1 カーネルは 1 タイルあたり 4 グループ、各グループが grid への
`vgather` を 2 本使う。Phase 49.5 の実装は両方を同じ scratch スロット
(`scratch[0]`, `scratch[1]`) に落とし、その 2 本をすぐ読み戻していた。
つまり gather の latency を 1 タイルで 4 回払っていた。

IQ3_S / IQ3_XXS は Phase 49 で「タイルの 8 本を先に全部出し、その後で読む」形に
直して 14.47 -> 28.02 GB/s を得ている。IQ2 側は同じ形になっていなかった。

IQ2_XS / IQ2_XXS は 1 グループあたり 4 本 (grid 2 + sign 2)、タイルで 16 本。
スロットは 4 本分しかなかった。

### 変更

`ggml/src/ggml-hexagon/htp/hvx-mm-kernels-tiled.h`

- `iq2_s_gather_group()` と `iq2_s_finish_group()` に分割した。gather の発行と
  読み戻しを分けたので、タイルの 8 本を先に全部出せる。
- `iq2f_gather_group()` と `iq2f_finish_group()` も同様に分割した。こちらは
  2 グループずつ 2 パスに分け、8 本を同時に飛ばす。16 本を一度に生かすと
  レジスタが足りなくなるため、あえて半分ずつにした。
- スカラー経路は `iq2_s_unpack_group_8k_scalar()` /
  `iq2f_unpack_group_8k_scalar()` として残した。`scratch == NULL` のときの
  挙動は変えていない。

`ggml/src/ggml-hexagon/htp/matmul-ops.c`

- `IQ2S_SCRATCH_STRIDE` を 512 から 1024 にした (スレッドあたり 4 本 -> 8 本)。
  IQ2 ファミリは同じスロットを共有する。
- VTCM 予約は 128 KiB 固定で、使用量は 44288 -> 49408 バイト。予約内に収まる。
  ホスト側が引く定数は変わらないので、op データ用の VTCM は減っていない。
  `_Static_assert` で全領域の非重複と予約内を検査している。

コミット `f348c6100`。

### 符号マスクの算術化 (skel D)

IQ2_XS / IQ2_XXS は 1 グループにつき grid 2 本と sign 2 本の計 4 本の `vgather`
を使っていた。sign は `ksigns64` (128 エントリ x 8 バイト) の参照で、
**この表は 7 bit インデックスの偶数パリティ展開**である。つまり
バイト j (j<7) は「インデックスの bit j が立っていれば 0xff」、バイト 7 は
「パリティが奇数なら 0xff」。128 件すべてを検査して一致を確認した
(`p50_ksigns_check.py`、不一致 0、部分バイト 0)。

そこで sign の 2 本を算術に置き換えた。低い 4 バイトは bit 0-3 を、
高い 4 バイトは bit 4-6 とパリティをバイトへ広げる。IQ2_S が既に使っている
`iq2_s_sign_mask_arith()` を再利用している。**gather は 4 本から 2 本になる。**

| 型 | C (sign も gather) | D (sign は算術) | 変化 |
|---|---:|---:|---:|
| IQ2_XS | 9.61 GB/s / 18302 us | **10.85 GB/s / 16207 us** | **+12.9% / -11.4%** |
| IQ2_XXS | 8.57 GB/s / 14517 us | **9.25 GB/s / 13452 us** | **+7.9% / -7.3%** |
| IQ2_S | 14.17 / 41280 | 14.17 / 41283 | 0.0% (対照) |
| IQ3_S | 28.12 / 108961 | 28.12 / 110336 | -0.0% (対照) |
| IQ3_XXS | 22.00 / 152887 | 21.98 / 153036 | -0.1% (対照) |
| 合計 | 414777 | 413476 | -0.3% |

**logits は `f3a0d235...` で C と完全一致** (2 run とも)。演算順序を変えていないので
ビット一致が期待どおり得られている。触っていない IQ2_S と IQ3 が 0.1% 以内で

全体への効果は小さい。IQ2_XS + IQ2_XXS の DSP 時間は 32819 -> 29659 us (4 step) で

**部品では +13% / +8% だが、モデル全体では 0.1% 級**である。

D を既定にしてよいかの確認として 8 step を 2 回回した。1 回目は `exit 0` で
step 1-7 の中央値 759.1 ms (停止 1 回を含む)、2 回目は 2 step で `exit 6`
(swap-out ガード)。この時間帯は環境が悪化しており (毎 run に数秒の停止)、
C との差は分解できない。**悪化の機構が無いこと** (同じ op を同じ順序で実行し、
DSP の合計時間は C より短く、logits はバイト一致) を根拠に採用する。
時間で優位を示したのではなく、厳密に仕事が減ることを根拠にしている。

### 測定方法の注意 (非同期の時間帰属)

`GGML_SCHED_SPLIT_TIMING=1` の `ggml-sched-split` は、この構成
(`OPPOLL=0`、非同期投入) では DSP の実演算時間を含まない。実測例:

```
ggml-sched-split id 0 backend CPU  nodes 2950 avg_us 587123 sync_us 0 copy_us 0 compute_us 587123
ggml-sched-split id 1 backend HTP0:0 nodes  898 avg_us    352 sync_us 3 copy_us 7 compute_us    342
```

CPU 側 587 ms に対し HTP 側 0.34 ms で、これは投入の戻りだけである。
**この行から DSP 時間を読まない。** DSP 時間は `GGML_HEXAGON_PROFILE=1` の
op 別 `usec` の合計を使う。Phase 49.5 が「非同期投入を実行時間として
数えない」と決めたのと同じ扱い。

**一致。** つまり IQ2 カーネルの変更は分割経路の数値を変えていない。

なお、この分割時の値は**分割しない場合の `f3a0d235...` とは違う**。
行ごとに CPU と DSP が別々に計算するので、分割しない場合と一致する必要はない。
Phase 46 以来の「ビット一致」は**同じ分割設定どうしの比較**を指す。
今回確かめたのはそこであり、**変更前後で分割の出力が動いていない**こと。

`SPLIT=1` は既定にしていない (標準構成は `SPLIT=0`)。

### IQ2_XXS

NGL=9 では HTP 側に現れない (CPU 層にある)。NGL=24 で初めて現れ、
6.93 -> 8.59 GB/s。ファミリ側の変更がそのまま効いている。

## C. HTP 配置

### NGL 探索

`-ngl` は decode-probe の引数、それ以外の配置は `override-base.txt` (NGL=0) と
`override-l57.txt` (NGL>0、`blk.57.ffn_up.weight` を HTP へ) で決まる。

cap 2112000 / 1862400、8 step、noreplay。同じ cap で `mid_stable YES` の run だけを使う。

**推定子は「run ごとの最小 step の、run 間の中央値」**にした。理由は実測:

- 同じ NGL=16 でも `med_all` は 686.1 と 880.6 で **28% 違う** (p2 と p5)。
  停止の入り方で中央値が動くためで、この環境では中央値が使えない。
- 同じ 2 run の**最小 step は 615.1 と 617.3 で 0.3% しか違わない**。
  停止は step を遅くするだけなので、最小値は停止の無い計算時間を映す。
- NGL=16 と NGL=24 の最小値の範囲は重なる (497.6-626.9 と 591.1-622.2)。
  したがって 2% 級の優劣は決められない。

| NGL | run 数 | 最小 step の中央値 ms | 範囲 | 対 CPU 単独 |
|---:|---:|---:|---|---:|
| 0 (CPU 単独) | 6 | 681.3 | 668.7 - 729.6 | - |
| 16 | 9 | 615.0 | 497.6 - 626.9 | **-9.7%** |
| 24 | 6 | 600.8 | 591.1 - 622.2 | **-11.8%** |
| 28 | 1 | 627.1 | - | -8.0% |

- NGL=16 vs NGL=0: **-9.7%**
- NGL=24 vs NGL=0: **-11.8%**
- NGL=24 vs NGL=16: -2.3% (範囲が重なるので決められない)
- NGL=28 vs NGL=16: +2.0% (遅い側)

**結論: 16 と 24 は 2% 級の差で、ばらつきの範囲が重なるため優劣を決められない。
どちらも CPU 単独より 10-12% 速い。28 は 16 より遅い。**
「NGL を増やすほど速い」とは言えないし、「16 が最良」とも言えない。
Phase 49.5 が cap 1785600 で測った「1 層あたり CPU 22.8 ms 減 / DSP 8.1 ms 増」は、
この cap と層構成では 16 から 24 の間でほぼ相殺される。

外れ値の扱い: 中央値は停止で動くので使わない。**最小 step を使い、
run 間では中央値を取る**。1 run の異常値 (base1 の 497.6 など) は
run 間中央値では効かない。

生の step 列は端末の `p50-*.log` にあり、集計は `p50_ngl_robust.py`。

NGL=32 は同じ cap で `exit 6` (swap-out ガード)。再試行していない。
NGL=28 は `exit 0` で通り、ガードは発動しなかった。ガードは緩めていない。

### 層ごとの損益

Phase 49.5 の cap 1785600 での実測は 1 層あたり CPU 22.8 ms 減 / DSP 8.1 ms 増。
今回は NGL 16 と 24 の差がばらつきに埋もれたため、**「NGL を増やすほど速い」
とは結論しない**。NGL=24 の DSP 時間は 1 token あたり約 154.6 ms (618430 usec / 4 step)、
NGL=9 は約 59 ms。層を増やすと DSP 側が比例して増えることは実測で確認した。

メモリ: NGL=32 で swap-out ガードに到達した。NGL=24 でも 8 step のうち 1 回
(12 run 中 3 回) ガードに掛かっている。NGL=16 が安定側。

### CPU スレッド数 (7 が最適。8 は大幅に悪い)

NGL=16、8 step で `P44_NTHREADS` を振った。各 2 run の中央値 (step 1-7)。

| threads | 中央値 ms | 対 7 |
|---:|---:|---:|
| 6 | 727.4, 717.0 | +7% |
| **7** | 631.9, 715.7, 684.7, 662.8 | - |
| 8 | 940.1, 951.7 | **+40%** |

**8 スレッドにすると 40% 遅くなる。** 8 コア全部を CPU の積和で埋めると、
HTP の駆動側 (FastRPC のホストスレッド) が回らず DSP に仕事を渡せなくなる。
6 スレッドも 7 より遅い。**7 が最適で、既定のままが正しい。**
「コアを全部使う」方向の変更はしない。

**理由がもう 1 つ分かった。** 測定ハーネス自身が 1 コアを使う。`run50.sh` は
stdout が変わるたびに `/proc` のスナップショットと `gguf-residency` を呼び、
**`gguf-residency` 1 回が実測 895 ms** かかる。THREADS=7 なら 7 + 1 = 8 コアで
ちょうど収まるが、THREADS=8 では 9 コア分になり、モデルのスレッドと
FastRPC の駆動スレッドが奪い合う。**スレッド数を変えるときは、
ハーネスが 1 コア使うことを忘れない。**

watcher 自体は THREADS=7 では無害だった。watcher あり/なしを 1 組ずつ取ると
最小 step は 651.4 (あり) と 617.4 (なし) で、これは NGL=16 の通常の範囲
(605-627) の内側で、差とは言えない。**停止の原因は watcher ではない。**

### 型・層ごとの損益 (3.1)

NGL=0 の計算グラフ (論理サイズ、実 DRAM 転送量ではない) を 16 層ごとに
型別へ集計した。合計 8183 MiB は Phase 49.5 の 8183 MiB と一致する。

| 層 | IQ2_S | IQ2_XS | IQ2_XXS | IQ3_S | IQ3_XXS | IQ4_XS | Q4_K | 合計 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 00-15 | 386 | 278 | 446 | 57 | 141 | 15 | 47 | 1630 |
| 16-31 | 483 | 317 | 320 | 21 | 453 | 0 | 0 | 1742 |
| 32-47 | 780 | 168 | 159 | 186 | 552 | 0 | 0 | 1908 |
| 48-63 | 232 | 143 | 21 | 576 | 947 | 178 | 141 | 2258 |
| output | - | - | - | - | - | 644 | - | 644 |

1 バイトあたりの処理効率 (DSP は今回の実測、CPU は Phase 49.5 の実測):

| 型 | DSP GB/s | CPU GB/s | DSP/CPU | 判定 |
|---|---:|---:|---:|---|

逆に、層 16-47 に多く残る IQ2_XXS (925 MiB) は CPU の方が速い。

損をする。** NGL=16 -> 24 で実測が +13 ms 悪化したのはこれで説明できる。

層 24-63 の CPU 側重みは 8183 - 2258 = 5925 MiB (310 テンソル)。
うち IQ2_XXS が 925 MiB あり、これは動かさない方が良い。

### 34 テンソ目の不具合の調査 (未再現、メモリで阻まれる)

`blk.63.attn_output.weight` が非同期分割で異常終了した件を、指示の範囲で
調べた (拡大はしていない)。

1. `run_split50.sh` は `NGL` を export しないと `run49.sh` の `${NGL:-23}` で
   **-ngl 23** になる。この構成は `CPU_Mapped 8774.90 + HTP0:0 3397.94 MiB` を
   要求し、ロード中に swap-out ガードで `exit 6` (wall 12.80 秒、decode 0 step)。
   **分割の試験では NGL を明示すること。**
2. `NGL=0` を明示して `SPLIT=1 async` で回すと `exit 0` だが、
   `sched_reserve: splits = 1` で HTP 側の分割ができていない
   (テンソルが CPU に載っているため)。しかも decode が
   **step 0 12,850 ms / step 1 12,867 ms** と 19 倍に退化した。クラッシュも
   DSP エラーも出ていない。
3. したがって**元の異常終了は再現できていない**。再現にはこのテンソルが
   実際に HTP に載る構成 (49-57 層以上のオフロード) が要るが、
   それはこの端末のメモリに収まらない (NGL=23 で既にガード)。

**結論: 34 テンソ目の不具合は、この端末のメモリ容量の中では再現できない。**
原因究明を進めるには、より小さいモデルか、より大きいメモリの端末が要る。
分割を拡大しないという制約は維持する。

### 選択的配置 (3.3)

**試験したうえで採用しない。**

NGL=16 のグラフは `splits = 2`（CPU が層 0-48、HTP が層 49-63）。ここで層 36 の
FFN 3 本（`ffn_gate` / `ffn_up` / `ffn_down`、約 110 MiB、IQ3_S と IQ3_XXS）だけを
`override` で HTP へ移す試験をした。この 3 本は CPU 側に残る中で最も効率差が
大きい型（IQ3_S 6.4x）である。

結果:

| 項目 | 無変更 | 層 36 を HTP へ |
|---|---|---|
| `splits` | 2 | **4** |
| override されたテンソル | 1 (blk.57、NGL=16 では無効) | 3 |
| 最小 step | 498-620 ms | **639-681 ms** |
| step 1-7 の中央値 | 635 ms | 684 ms |

**split が 2 から 4 に増え、速くならなかった。** 110 MiB を移して得られる数 ms に
対し、split 境界ごとの固定費（HTP ディスパッチの往復）が上回る。層は逐次依存なので、
CPU 区間の中に 1 枚置くたびに境界が 2 つ増える。

さらに、CPU 側に残る 1410 MiB の IQ3 系ですら、移す価値のある量をまとめて動かすには
層をまたぐ分割が要る。**「層の上から N 枚」という一律配置から離れない。**

測定環境の都合でこの比較は ±8% のばらつきの中にあり、差の大きさは確定できない。
言えるのは「split が倍になり、改善は観測されなかった」ところまで。
機構からは損失が予測されるので、既定にはしない。

## G. 生成品質

性能とは分けて書く。**数値的に測れた範囲では大きな劣化は無いが、
品質が同等であるとは結論しない。**

### 固定した評価データ (結果を見る前に確定)

| id | 内容 | sha256 | 大きさ |
|---|---|---|---|
| eval A | `docs/build.md` の散文 (英語) | `39D522EAC213B3D375E446D172D86BED333E744E754C07E8EF08BA8DBC8393E4` | 1432 バイト |
| eval B | Phase 49.5 報告の散文 (日本語) | `F7779E4B29465325D62CF99BA2B3A83C2B2E3ADFFE26A9DF992F0217E8D322CC` | 1218 バイト |

eval B は 2026-11-09 に書いた文章なので 27B の学習データには入っていない。
eval A は公開リポジトリの文書なので、学習データに含まれる可能性を排除できない。
どちらも CPU と HTP に**同一のトークン列・同一の文脈長**を与えているので、
比較の妥当性は保たれる。絶対値の解釈には注意が要る。

方法: `llama-perplexity`、`-c 128 --chunks 1 -b 128 -ub 128 -t 7 --no-warmup`、
同じモデル・同じファイル。CPU は `-ngl 0`、HTP は `-ngl 24`。
これはベンチ用の `override` を使わない経路なので、decode ベンチとは
配置が一致しない。品質の比較としてのみ読む。

### 結果

| データ | CPU 単独 PPL | HTP NGL=24 PPL | 差 | 99 秒あたり |
|---|---:|---:|---:|---|
| eval A | 17.4010 +/- 6.52719 | 17.5083 +/- 6.59441 | **+0.62%** | 96.72 -> 74.08 秒 |
| eval B | 33.3871 +/- 14.07957 | 33.9855 +/- 14.37350 | **+1.79%** | 96.85 -> 75.09 秒 |

点推定では HTP の方が 0.6% と 1.8% 高い。ただし 1 chunk = 127 トークンの
perplexity で、表示される区間は ±37% と ±43%。**この測定は 1% 級の差を
分解できる力を持たない。** 「悪化した」とも「同等」とも言えない。
言えるのは「桁で悪化してはいない」ところまで。

perplexity の壁時計が -23% / -22% なのは prefill が batch 128 で走るためで、
decode の改善として計上しない。

| 量 | 結果 |
|---|---:|
| 平均 NLL CPU | 4.778922 |
| 平均 NLL HTP | 4.779550 |
| **平均差 (HTP - CPU)** | **+0.000628 nats** |

### なぜ n=16 で止めたか (環境の上限)

n を増やせば NLL の区間は狭くなる (n=64 なら SE 0.011)。試した結果:

| replay 長 | 結果 |
|---:|---|
| 4 | `exit 0`、完走 (標準列) |
| 16 | `exit 0`、完走 (本命の n=16) |
| 32 | 走り出すが **13 step で swap-out ガード** (`exit 6`) |
| 64 | **`exit 2`、probe の stdout が空**、wall 2.7 秒 (2 回試して同じ) |

32 step が 13 step で落ちるのは、run が長いほど swap-out の累積が
1024 MiB に届くため。64 step は probe が起動していない (stdout に
`OVERRIDE` も `PHASE load_begin` も出ない) ので、ガードではなく
probe 側の別の理由。原因は特定していない。

## H. 安全性

- swap-out ガード (1024 MiB) は緩めていない。掛かった run は捨てた。
  exit 6 は NGL=32 で 1 回、NGL=24 で 3 回、NGL=16 で 0 回。
- MemAvailable は run 開始時に 9.9-11.3 GB、終了時 11.0-11.8 GB。
  `run49.sh` の前提 (9,500,000 kB) を満たさない run は実行されていない。
- DSP 異常なし。非有限 logits なし。
- 端末の温度保護・ZRAM・重要サービスは変更していない。cooling_device は
  すべて `cur_state 0` のまま。書き込みはしていない。
- 背景アプリは Phase 49.5 の 6 パッケージに加えて、anon page を持つ利用者
  アプリ 11 個を `am force-stop` した (systemui / system / thermal / ZRAM は
  触っていない)。名前は `p50_run.sh` にある。すべて利用者が開けば戻る。
- 画面と充電の状態は試験のために変えた。`screen_off_timeout` は 1800000 に
  していたので 30000 に戻す。`svc power stayon` も戻す。

### メモリの床 (安全性と測定精度の両方に効く)

この端末は 16 GB しかなく、NGL=16 では mmap 8.66 GB + HTP のタイル化コピー約 2.26 GB
+ 常駐アプリ約 2.2 GB で `MemFree` は 200 MB 前後になる。実測:

- 1 run あたり 400-840 MiB の swap-out が出る。ガード (1024 MiB) の内側だが近い。
- 1 run に 1-2 回、**2-10 秒の停止**が入る。中央値は動かないが、最大値は大きく振れる。
- アプリを追加で止めても `AnonPages` は 1 GB 前後までしか減らない。
  `MemAvailable` が 11 GB あっても `MemFree` が 200 MB なので、走行中に
  page reclaim が発生する。これが run 間ばらつき ±8% の主因。
- したがって **1-2% の差を run 全体の時間で判定しない。** 部品 (op 別 usec) で示す。

**停止の正体**: モデルのページが run の途中で page cache から落ち、decode 中に
再フォールトしている。実測で、アイドル時に HTP が使う範囲の residency は
**68.7%** (`resident 1030646 / pages 1499463`) まで下がっていた。
`run49.sh` のゲートは 95% を要求するので prewarm で戻すが、run 中にまた落ちる。
**メモリ不足そのものが原因で、ハーネスの副作用ではない**
(watcher を止めても停止は消えなかった)。

### 環境が測れなくなった最後の記録

セッション後半 (2026-11-10 04:20 以降) は、**6 run 連続で全部 CAP_CHANGED**
になった。内訳:

cap は下がるだけでなく**上がることもある** (q4 で 3513600 まで)。ただし

**Dozing の低い段 (883200) も再現しなかった。** セッション序盤に 883200 を

## J. 次の一手

1. **fast cap を取れる状態のときだけ比較する。** cap が 3628800 / 4608000 に
   戻る条件は未解明。戻った瞬間に 8 step を `0, 16, 24, 24, 16, 0` の
   回文順で取る。**待ち受けは `p50_fastcap.sh wait <秒>` に用意した**:

   なった瞬間に系列を回す (窓は 10 分程度しか続かないため、人が見張ると間に合わない)。
   片側だけの順序だと後半の run が 5% 程度有利に出る (g1 741.9 -> g3 700.3 は
   同じ NGL=0)。判定は**run ごとの最小 step の run 間中央値**で行う。
   中央値は停止で 28% 動くので使わない。
2. **IQ2 は打ち止め。** gather の先行発行 (IQ2_S +38.8%、IQ2_XS +41.3%、
   IQ2_XXS +33.7%) と符号マスクの算術化まで入れた。残る DSP 時間は

3. **配置は層単位から離れない。** 16 と 24 は 2% 級で決められない。28 は遅い。
   32 はガード。テンソル単位の選択配置は実際に試して split が 2 -> 4 になり、
   速くならなかった。CPU 区間に HTP テンソルを 1 枚置くたびに境界が 2 つ増える。
4. **残る大物は CPU/DSP の重なり (最大 -16%)。** DSP は 1 token の 84% で
   遊んでいる。重なりを作る道は 1 テンソル内の row split (Phase 46 の機構) だけで、
   `blk.63.attn_output.weight` の異常終了の原因が未解明のまま拡大できない。
   **今回は再現を試みて、メモリで阻まれることが分かった** (このテンソルが HTP に
   載るには 49-57 層のオフロードが要り、NGL=23 で既にガード)。
