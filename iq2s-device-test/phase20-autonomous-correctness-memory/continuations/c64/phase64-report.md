## §1 目標1: Op Fusion rework 導入 - **BLOCKED（依存連鎖、§1.1 が理由）**

### §1.1 決定的な発見: Op Fusion は単独では入らない

Phase 62 は「Op Fusion rework（#30843）が `htp-kparams.cpp` を導入する基盤で、
これを入れれば SGN/DSV4/LIGHTNING_INDEXER が解禁される」と整理していた。
**この理解は不正確だった。** 実測すると:

- #30843 は上流 hexagon 系列の **63 コミット中 26 番目**（古い順）。
- つまり **25 コミットの先行を要求する**。
- さらに、その 25 のうち **16 番目が repack rework（#30635）**であり、
  **目標2 が目標1 の前提**になっている。
- 依存は「提案」ではなく**コンパイル依存**: #30843 を単独で cherry-pick すると
  **25 ファイル・76 ハンク**の競合が出る。しかもその多くは
  「fork が消した」ではなく「**fork がまだ持っていない**」
  （`concat-ops.h`・`cpy-ops.h`・`gather-rows.c`・`im2col-ops.h` は fork に存在しない）。

```
$ git cherry-pick -n 643b0cdac
CONFLICT ... 25 files
$ # 例: ggml/src/ggml-hexagon/htp/concat-ops.h は HEAD に存在しない
```

**したがって Phase 62 の「基盤を入れれば解禁群が入る」という見立ては、
実際には「25 コミットの連鎖を順に通す」ことを意味していた。**
Phase 65 の計画はこの前提で組み直す必要がある（§7）。

### §1.2 なぜ Op Fusion に到達しなかったか

時間の使い方の判断: 25 コミット鎖のうち **19 コミットは通した**
（うち 13 は Phase 62/63 で既取り込み）。残り 6 コミット + 76 ハンクの
Op Fusion 本体に届かなかった。理由は §4 の熱問題で実機検証に時間を取られたため。

**中途半端に 76 ハンクを埋めて壊れた状態を残すより、
動く状態で 6 コミット分の前進を確定させた**（§2・§3）。

### §2.3 競合の解決記録

**`dma-queue.{c,h}`（#29971）** 2 ハンク。このコミットは Phase 62 で取った
#31442 より**古い**ので、上流側が `dma_queue_push_fallback_contig` と
2 変種の `dma_queue_push` を再追加しようとする。fork は既に統合版を持つので
**HEAD を採用**。安全な理由: `ssm-conv.c` は `dma_queue_push` しか呼ばず、
統合版は HVX<75 でも挙動等価（`DMA_MAX_2D_ROW_SIZE` が 16 bit 上限、
`dma_ring_push_single_contig` が 1d に落ちる）。

**`hex-utils.h`（#30067）** 1 ハンク。上流は `hex_l2flush` を手動の
`Q6_dccleaninva_A` ループに置き換えるが、fork は `qurt_mem_cache_clean` を使う
**修正済み版**（戻り値 `int`、アラインメントループ無し）を持つ。**HEAD を採用。**

**`htp-ops.h`（#30104/#30115）** 2 ハンク（同時適用で重なった）。上流が
`HTP_OP_UNARY_GELU_QUICK` を追加する位置に fork は CEIL/UPSCALE を持つ。
**3 つとも残した。**

**`matmul-ops.c`（#30035 ほか）** 1 ハンク。dispatch 表で、上流は
`q2_k` のタイルサイズを 512→336 に変える。fork は 4 列カーネル用の第 4 引数を
持つ行が 4 つ多い。**fork の全行と第 4 引数を残し、`q2_k` だけ 336 を採用。**
整合性を確認: 4 つの表すべてが 336、`HTP_MM_WEIGHT_TILE_SIZE_Q2_K 336`、
新設の `HTP_MM_WEIGHT_ALIGNED_TILE_SIZE_Q2_K 384` も一致。

### §9.1 前面アプリ保護の強化（本 Phase で追加）

指示「フォアグラウンドのアプリは kill するな」を受けて、`p53_run.sh` の
kill ループを**フェイルセーフ化**した:

- **`FG` が読めないときは 1 つも止めない**（従来は空だと全リストを止めていた）。
- **各 `am force-stop` の直前に foreground を読み直す**（切替の競合を閉じる）。
- 途中で読めなくなったら打ち切る。

```
P55_KILL_SKIPPED no readable foreground, stopping nothing
P55_SKIP_FOREGROUND <pkg>
```

実測: 本 Phase の run では `P55_SKIP_FOREGROUND net.waterfox.android.release` が
記録され、前面アプリは止まっていない。旧版は `p53_run.sh.bak-c64` に残置。

### §9.2 swap guard の発動

初回の 32-step が **exit 6**（pswpout 増分 2,481,794 pages = 9.46 GB）。
22 時間の idle 後の**冷キャッシュ**が原因で、Phase 57/59/60 と同じパターン。
指示どおり除外し、再試行（605,055 pages）を採用した。
