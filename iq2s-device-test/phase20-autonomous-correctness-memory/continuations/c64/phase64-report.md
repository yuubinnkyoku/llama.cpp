## §1 目標1: Op Fusion rework 導入 - **BLOCKED（依存連鎖、§1.1 が理由）**

### §1.1 決定的な発見: Op Fusion は単独では入らない

Phase 62 は「Op Fusion rework（#30843）が `htp-kparams.cpp` を導入する基盤で、
これを入れれば SGN/DSV4/LIGHTNING_INDEXER が解禁される」と整理していた。
**この理解は不正確だった。** 実測すると:

- #30843 は上流 hexagon 系列の **63 コミット中 26 番目**（古い順）。
- つまり **25 コミットの先行を要求する**。
- さらに、その 25 のうち **16 番目が repack rework（#30635）**であり、
  **目標2 が目標1 の前提**になっている。
- 依存は「提案」ではなく**コンパイル依存**: #30843 を単独で cherry-pick すると
  **25 ファイル・76 ハンク**の競合が出る。しかもその多くは
  「fork が消した」ではなく「**fork がまだ持っていない**」
  （`concat-ops.h`・`cpy-ops.h`・`gather-rows.c`・`im2col-ops.h` は fork に存在しない）。

```
$ git cherry-pick -n 643b0cdac
CONFLICT ... 25 files
$ # 例: ggml/src/ggml-hexagon/htp/concat-ops.h は HEAD に存在しない
```

**したがって Phase 62 の「基盤を入れれば解禁群が入る」という見立ては、
実際には「25 コミットの連鎖を順に通す」ことを意味していた。**
Phase 65 の計画はこの前提で組み直す必要がある（§7）。

### §1.2 なぜ Op Fusion に到達しなかったか

時間の使い方の判断: 25 コミット鎖のうち **19 コミットは通した**
（うち 13 は Phase 62/63 で既取り込み）。残り 6 コミット + 76 ハンクの
Op Fusion 本体に届かなかった。理由は §4 の熱問題で実機検証に時間を取られたため。

**中途半端に 76 ハンクを埋めて壊れた状態を残すより、
動く状態で 6 コミット分の前進を確定させた**（§2・§3）。

**`dma-queue.{c,h}`（#29971）** 2 ハンク。このコミットは Phase 62 で取った

**`htp-ops.h`（#30104/#30115）** 2 ハンク（同時適用で重なった）。上流が
`HTP_OP_UNARY_GELU_QUICK` を追加する位置に fork は CEIL/UPSCALE を持つ。
**3 つとも残した。**

**`matmul-ops.c`（#30035 ほか）** 1 ハンク。dispatch 表で、上流は
`q2_k` のタイルサイズを 512→336 に変える。fork は 4 列カーネル用の第 4 引数を
持つ行が 4 つ多い。**fork の全行と第 4 引数を残し、`q2_k` だけ 336 を採用。**
整合性を確認: 4 つの表すべてが 336、`HTP_MM_WEIGHT_TILE_SIZE_Q2_K 336`、

## §12 追記2: **tiled 既定 ON は退行だった（重大）**

Phase 63 は tiled の ARM 既定を ON にしたが、**そのとき tiled ON と OFF を
測っていなかった**（「1 token では発動しないので hash が変わらない」ことだけを確認した）。
本 Phase で測ったところ、**既定 ON は CPU prefill を 25% 遅くしていた。**

### §12.1 測定

条件: NGL=0（CPU のみ）、prefill 128、同一バイナリ（`1cc02638`）、
`GGML_CPU_TILED_MM` だけを切り替え、cap 1,996,800 に揃った run のみ採用。

| env | prefill_ms（4 run） | 中央値 | cpu_split_us |
| --- | --- | --- | --- |
| **`GGML_CPU_TILED_MM=1`** | 113,892.78 / 114,363.58 / 114,578.02 / 115,782.22 | **114,470.8** | 29.3-30.3 M |
| **`GGML_CPU_TILED_MM=0`** | 90,918.64 / 90,989.06 / 91,704.70 / 96,374.35 | **91,346.9** | 23.4-24.1 M |

**比 = 1.2531。tiled ON は 25.3% 遅い。**

**この 2 群は非常によく分離している**（ON は 113.9-115.8 の狭い範囲、
OFF は 90.9-96.4）。`cpu_split_us` も同じ方向（ON が 27% 多い）なので、
**測定誤差ではなく実体**である。

（cap が違う run は除外した。1,555,200 に落ちた run は ON 151,059.97 で、
これは cap の差で遅いだけ。）

### §12.2 Phase 61 の 2.14 倍との矛盾

同じ測定を Phase 61 は CPU `318508e8`（c60 ソース）で行い、**逆の結果**を得ていた:

| CPU | OFF | ON | 比 |
| --- | --- | --- | --- |
| `318508e8`（c60、Phase 61） | 111,087.29 | **51,971.70** | **ON が 2.14 倍速い** |
| `1cc02638`（統合、本 Phase） | 91,346.9 | 114,470.8 | **ON が 25% 遅い** |

**読み取れること**:
- **統合で tiled を使わない経路は速くなった**（111.1 s → 91.3 s、18% 改善）。
  これは Phase 62 の統合が効いている証拠。
- **統合で tiled を使う経路は大幅に遅くなった**（52.0 s → 114.5 s、2.2 倍悪化）。

**したがって「Phase 62 の統合が tiled 経路を壊した」可能性が高い。**
ただし**機構は特定していない**（§12.3）。

### §12.3 機構は未特定

考えられる原因（**いずれも未検証**）:
1. Phase 62 で入れたコミットのどれかが tiled の前提（タイル形状・repack 前提）を変えた。
2. `GGML_CPU_TILED_MM=0` で wdata 予約（64 + 8×512 KB ≒ 4 MB）が消えることが
   効いている（メモリ圧の高い端末では 4 MB の確保が 25% の差を生むとは考えにくいが、
   ページフォールトの連鎖はあり得る）。
3. tiled が実際には発動しておらず、ON 側は予約のオーバーヘッドだけを払っている。
   → この場合 ON と OFF の差は「発動していないのに遅い」ことになり、
   さらに深刻（予約だけで 23 s は説明しにくい）。

**切り分けには `ggml_tiled_min_batch` の発動を数える計装が必要。** 未実施。

### §12.4 対策: `GGML_CPU_TILED_MM=0` を運用既定にした

**hash への影響を確認した**: `GGML_CPU_TILED_MM=0` で 32-step を取ると
**`e788051e`（標準と同一）**。Phase 63 の「フラグは hash を変えない」という
観測と一致する。**つまり無コストで 25% を取り戻せる。**

`run53.sh` の env ブロックに**上書き可能な既定**として追加した:

```sh
GGML_CPU_TILED_MM=${GGML_CPU_TILED_MM:-0} GGML_HEXAGON_DEVICES=HTP0:0 ...
```

- 既定は `0`（退行を避ける）。
- 明示的に `GGML_CPU_TILED_MM=1` を渡せば従来どおり tiled を通せる（実験用）。
- 旧版は `run53.sh.bak-c64t` に残置。
- 反映後の確認: 32-step が `e788051e` のまま（1 回実測）。

### §12.5 推奨

**コードの既定（Phase 63 で `true` にした `ggml_tiled_matmul_enabled`）も
`false` に戻すべき。** ただし本 Phase では**スクリプト側で回避するに留めた**。
理由:

- コードの既定を戻すと、Phase 63 の「既定 ON」という決定を覆すことになり、
  その判断には**機構の特定**が必要（§12.3 が未解決）。
- スクリプト側の `env` 既定で運用上の損失は既に止まっている。

**Phase 65 の最優先項目として「tiled 退行の機構特定と既定の再判断」を挙げる。**
具体的には `ggml_tiled_matmul_enabled` の発動回数カウンタを入れ、
llama-cli/probe で何回 tiled パスに入ったかを実測する。

### §12.6 llama-cli での傍証

同じ現象を llama-cli でも観測した（1 桁精度なので弱い証拠）:

| 周 | tiled ON | tiled OFF | cap（ON / OFF） |
| --- | --- | --- | --- |

| 2 | 2.4 t/s | **2.7 t/s** | 2,227,200 / 1,996,800 |

**2 周とも OFF が速く、しかも OFF の方が cap が低かった。** 方向は一致する。

### §12.7 Phase 63 の記述の訂正

Phase 63 §3.2 は「1 token では tiled 非通過なのでフラグは wdata 予約に影響せず、
hash は変わらない」と書いた。**hash については正しかった**（本 Phase で再確認）。

### §16.3 判定: **実質差なし。決着。**

**決定的な根拠は「符号が反転したこと」である:**

**6 run では「50 が速い」、12 run では「50 が遅い」。** これは

t=1.77 で有意水準に届かず、IQR は 94 と 222（50 の方が 2.4 倍ばらつく）。

1. **IQ2/IQ3 の repack 27 関数を新しい枠に移す先が無い。** 上流のフレームワークは

   そのまま使えない。
2. **取り込むと IQ2/IQ3 が tiled でなくなる**（＝ CPU フォールバックに戻る）。
   これは 262 分割の状態に自分から戻すことを意味する。
3. **q2_K は rework 無しで既に動いている**（§2.1）。rework の便益のうち

Op Fusion（#30843）は repack rework の**後**に位置し、rework の新フレームワーク

Op Fusion も取れない。**

**目標1 を達成する唯一の道**は次のどちらかであり、**どちらも Phase 65 の

- **(b) 上流の Op Fusion だけを fork の repack 層に移植する。**

### §17.7 この節の位置づけ

**「取れなかった」ではなく「取らないと決めた」**である。理由は競合の多さではなく、
**上流のフレームワークに fork の中核機能の枠が無い**という機能的な事実。

### §17.8 §17.6 の推奨を訂正する

§17.6 で「Op Fusion のうち `htp-kparams.cpp` と RMS_NORM_MUL fusion だけを
個別に移植するのが安い」と書いた。**これを実測で確認したところ、間違いだった。**

- `htp-kparams.cpp` は **2,811 行**。
- 中身は**テンプレートメタプログラミング**で、各 op が
  `SolveFn(args..., &kparams)` という**統一シグネチャの solve 関数**を持つことが前提:

```cpp
template <auto SolveFn, typename... Args>
static inline bool htp_kparams_check(Args &&... args) {
    decltype(htp_kparams_type(SolveFn)) kparams;
    return SolveFn(std::forward<Args>(args)..., &kparams);
}
```

- **その統一 solve シグネチャを作るのが #30843 そのもの**である
  （上流は全 op を solve パターンに書き換え、`htp_kparams_solve` から
  テンプレートでディスパッチする）。
- fork の op は独自シグネチャの solver（`htp_mm_hvx_solve_vtcm_params` 等）を
  持つが、kparams が要求する形ではない。

**したがって「kparams だけ抜く」は成立しない。** kparams を入れるには
全 op の solve 化（＝ #30843 の本体）が必要で、それは repack rework の上に載っている。

**訂正後の選択肢は実質 1 つ**:

- **(a) 上流フレームワークを採用し、IQ2/IQ3 をその上に再実装する。**
  §17.2 の 27 関数の書き直し + 上流 rework の取り込み（99 ハンク）。
  工数は大きいが、以後の上流追従は楽になる。
- **(b') fork の repack 層を保ったまま、上流の Op Fusion を手で移植する。**
  kparams のテンプレート機構を fork の solver 群に合わせて書き換える必要があり、
  実質「上流の fusion を fork 用に再設計する」作業。工数は (a) と同程度かそれ以上で、
  しかも上流との差分は広がり続ける。

**どちらも Phase 65 の設計判断**であり、本 Phase では決めない。
**判断材料として確実なのは「安い道は無い」ということ**である。
§17.6 の「(b) が安い」は撤回する。

## §21 追記9: **§19 の撤回をさらに撤回する（cap を揃えて再測定）**

報告書の中で同じ問題を 2 回訂正することになった。経緯を正直に残す。

- **§12**: 「tiled 既定 ON は 25.3% 遅い」と判定（cap 1,996,800 に揃えて各 4 run）。
- **§19**: 計装で発動（12,800 calls）を確認し、測り直したら 86-185 s と振れたので
  **§12 を撤回**した。
- **§21（本節）**: §19 の再測定は **cap を記録していなかった**。
  cap を揃えて測り直したところ **§12 が再現した**。**§19 の撤回が誤りだった。**

### §21.1 何を間違えたか

§19 の 6 run は cap が 1,113,600〜2,496,000 の間で動いていた。**cap が 2.2 倍違えば
prefill も 2 倍近く変わる。** したがって §19 の「86-185 s のばらつき」は
**熱による cap 変動そのもの**であり、tiled の効果を覆す証拠にはならなかった。

**プロジェクトの規則「比は同一セッション近接run（ABBA推奨）で cap を必ず記録」に
自分で違反していた。** §19 で cap を記録しなかったのが誤りの原因である。

### §21.2 cap を揃えた再測定（独立セッション）

計装ビルド（`9a8c95cd`）で、cap を各 run の前後で記録し、
**cap 1,996,800 で安定した run のみ**を採用:

| tiled | prefill_ms | cap |
| --- | --- | --- |
| **OFF** | 91,671.53 | 1,996,800-1,996,800 |
| **OFF** | 92,132.15 | 1,996,800-1,996,800 |
| **ON** | 113,977.75 | 1,996,800-1,996,800 |
| **ON** | 116,492.14 | 1,996,800-1,996,800 |

| 指標 | 値 |
| --- | --- |
| OFF 平均 | 91,901.8 |
| ON 平均 | 115,234.9 |
| **比** | **1.2539 → ON が 25.4% 遅い** |

**§12 の 25.3%（OFF 91,346.9 / ON 114,470.8）とほぼ完全に一致した。
独立したセッションで再現したので、これは実体である。**

（採用しなかった run: ON @ cap 2,496,000-2,227,200 = 87,698.13、
OFF @ cap 2,227,200-1,996,800 = 163,378.19。どちらも cap が揃っていない。）

### §21.3 確定した結論

1. **tiled は発動している**（12,800 calls、計装で確認）。
2. **tiled は cap を揃えると 25% 遅い**（2 セッションで再現、25.3% / 25.4%）。
3. **したがって `GGML_CPU_TILED_MM=0` を運用既定にする判断は正しい。**
   §19 で一度戻したが、**再適用した**（`run53.sh` に
   `GGML_CPU_TILED_MM=${GGML_CPU_TILED_MM:-0}`、旧版は `run53.sh.bak-c64t2`）。

### §21.4 Phase 61 の 2.14 倍との関係（未解決のまま）

Phase 61 は CPU `318508e8`（c60 ソース）で OFF 111.1 s / ON 52.0 s を測った。
今回は CPU `1cc02638`（統合）で OFF 91.9 s / ON 115.2 s。

- **tiled を使わない経路は統合で速くなった**（111.1 → 91.9 s、17% 改善）。
- **tiled を使う経路は統合で遅くなった**（52.0 → 115.2 s）。

**この非対称は説明できていない。** 候補は §12.3 に挙げた 3 つ（統合コミットが
タイル前提を変えた / wdata 予約 / 別の要因）だが、**いずれも未検証**。

**Phase 65 の課題**: `318508e8` と `1cc02638` の tiled パスを同一条件で比べ、
どこで 2.2 倍の差が生まれたかを bisect する。統合コミットは 10 件あるので、
`git bisect` で特定できる可能性が高い。

### §21.5 測定手順の教訓（最も重要）

**同じ間違いを 2 回しかけた。** 教訓を規則として残す:

1. **prefill の A/B では cap を必ず前後で記録し、揃った run だけを比べる。**
   cap が 2 倍違えば結果も 2 倍違う。揃っていない run を混ぜると、
   「ばらつきが大きい」と誤診して正しい結論を捨てる（§19 がそれ）。
2. **ばらつきを見たら、まず cap を疑う。** 熱の影響が先に来る。
3. 計装（`GGML_CPU_TILED_MM_COUNT`）は発動確認に有効。**入れておく価値がある。**

## §22 追記10: **Phase 62 以降の全ビルドが dotprod を失っていた（最重要）**

「tiled が 25% 遅い」という §12/§21 の結論を説明しようとして、**根本原因を発見した。**
**tiled の問題ではなく、ビルドの問題だった。**

### §22.1 発見の経緯

`318508e8`（Phase 60 の c60 ビルド）と現在のビルドで、同じソース・同じ cap なのに
tiled の速度が 3 倍違うことに気づいた:

```
git diff 842dbb917 49cc0dd15 -- ggml/src/ggml-cpu/   # 空（ソース同一）
```

ソースが同一なのに 3 倍違うので、ビルド構成を疑って CMakeCache を突き合わせた:

| ビルドディレクトリ | `GGML_CPU_ARM_ARCH` | 判定 |
| --- | --- | --- |
| `c60-neon`（Phase 60） | `armv8.6-a+dotprod+i8mm` | **正しい** |
| `c61m-neon`（Phase 61） | `armv8.6-a+dotprod+i8mm` | **正しい** |
| **`c62-test`（Phase 62）** | **`armv8`** | **dotprod 喪失** |
| **`c63-test`（Phase 63、標準に載せた `1cc02638`）** | **`armv8`** | **dotprod 喪失** |
| **`c63-fairA`（Phase 63 の比較用 A）** | **`armv8`** | **dotprod 喪失** |
| **`c64-nohex`（本 Phase の検証用）** | **`armv8`** | **dotprod 喪失** |

**原因**: `-DGGML_CPU_ARM_ARCH=armv8.6-a+dotprod+i8mm` をインラインの cmake コマンドで
渡していたが、シェル経由で値が壊れ、CMake が既定の `armv8` にフォールバックしていた。
Phase 61 で一度この症状（`CMake Warning: Ignoring extra path ... '.6-a+dotprod+i8mm'`）を
見ていたが、**Phase 62 以降は警告を見落としていた**。

### §22.2 機械的な証拠

`llvm-objdump` で dotprod/i8mm 命令を数えた:

| バイナリ | `sdot` | `smmla` |
| --- | --- | --- |
| `c64-dot`（正しいフラグで再ビルド） | **1,376** | **260** |
| `c63-test`（**標準に載せていた `1cc02638`**） | **0** | — |
| `c60neon2`（`318508e8`、Phase 60） | 1,376 | — |

**標準の CPU バイナリは Phase 62 以降ずっと dotprod 無しだった。**

### §22.3 なぜ 3 倍違ったか（tiled は SDOT を必要とする）

tiled の NEON マイクロカーネルは `vdotq_s32`（SDOT）を使う。
`__ARM_FEATURE_DOTPROD` が定義されないと**コンパイルされず、スカラーの
マイクロタイルにフォールバックする。**

| ビルド | tiled ON | tiled OFF | tiled の効果 |
| --- | --- | --- | --- |
| dotprod あり（`318508e8`） | **36.0 s**（3/3: 36.0/36.0/36.1） | ~126 s（cap 補正） | **3.5 倍速い** |
| dotprod なし（`1cc02638`） | 114.2 s | 91.4 s | **25% 遅い** |

**したがって「tiled が 25% 遅い」は dotprod 無しビルドの産物であり、
dotprod があれば tiled は 3.5 倍速い。** §12/§21 の結論は**前提が壊れていた。**
