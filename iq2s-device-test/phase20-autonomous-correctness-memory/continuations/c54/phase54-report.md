## §2 目標2: `iq3_s` の 32x2 共有化 — 単体テスト（先に実施）

Phase 53 では `iq3_s` の共有化を実機に入れて hash が変わり、撤回した。Phase 54 の指示は
**「まず単体テストで 1 行版 2 回と同一の出力を確認してから実機に入れる」**なので、
その順序で進めた。

### §2.1 何を確かめるか

Phase 53 の失敗は「共有化という変換が数学的に正しいか」と「DSP 実装がその変換を
正しく実現できているか」の**2 つを分離できていなかった**ことが問題だった。
単体テストは前者だけを切り出す。

`continuations/c54/iq3s_share_check.c` を書いた:

- `ref_32x1`: `tiled_vec_dot_iq3_s_scalar_32x1`（`hvx-mm-kernels-tiled.h:1361`）の
  構造をそのまま写した参照実装
- `shared_32x2`: 重み側（qh バイト・scale バイト・fp16 の d・符号バイト・グリッド index）を
  `(kt, row)` ごとに 1 回だけ計算し、2 本の活性に使う形
- 同じランダムタイル・同じ活性・同じグリッドを与えて、行ごとに比較

**注意:** x86 には `__fp16` が無いので、IEEE half を手で decode/encode している
（`half_to_float` / `store_half`）。DSP は `__fp16` をネイティブに使うが、
**このテストで見たいのは変換の同値性であって half の丸めではない**ので、これで足りる。

### §2.2 結果

```
$ clang -O2 -o iq3s_share_check.exe iq3s_share_check.c
$ ./iq3s_share_check.exe 200
trials 200 rows_per_trial 32
mismatched rows 0
worst abs diff 0
IDENTICAL
```

**200 試行 × 32 行 = 6,400 行で、1 行も差が出なかった。最大絶対差 0。**

**したがって「共有化という変換」は数学的に正しい。** Phase 53 で実機の hash が変わったのは、
**変換そのものではなく DSP 実装（HVX のレジスタ割り当て・`restrict`・scratch の別名・
コンパイラ差）に原因がある**ことになる。

### §2.3 この結果の意味（重要）

Phase 53 の §4.10(e) に書いた候補のうち、**「変換が間違っている」可能性は消えた。**
残る候補は:

1. `iq3_s_finish_group` が `scratch` を読み、`iq3_xxs` と違って `aux` ではなく `tile` を
   渡す。**共有化で `scratch` の寿命が変わる可能性がある。**
2. `iq3_s_scale_vector` が `tile` から `hvx_vmemu` で読む。**`tile` の読み出し位置が
   2 行で共有されると、HVX のロード順序が変わる可能性がある。**
3. `valid_rows` の扱い。

**いずれも「DSP 実装の詳細」であって、アルゴリズムではない。** 単体テストでは再現しない種類の
問題なので、**実機で切り分けるしかない。**

### §2.4 次の手順（実機）

単体テストが通ったので、指示の条件は満たした。実機に入れて 32-step hash を確認する。
ただし**目標1 の A/B が走っている間は skel を入れ替えられない**ので、A/B の完了後に実施する。

### §3.2 なぜ 1 組しか使えないのか（正直な原因）

**端末が 16:16 に再起動したため、このセッションは「冷えた状態」から始まった。**
Phase 53 の §9.5 で見つけた「最下段 `1113600` は 20 分以上動かない」という性質は、
**一度最下段まで加熱した後**の話であって、冷えた状態から始めると
`3628800 → 1785600 → 1670400 → 1555200 → …` と**段階的に降りていく**。
1 run が 5〜7 分かかるので、**1 組（2 run）の間に cap が動いてしまう。**

`p54_ab.sh` は最初に最下段まで待つループを入れたが、**600 秒待っても
`1113600` に到達せず**（冷えていたので）、そのまま測定に入った。これが失敗の原因である。

**1 組だけなので結論にはしない。** ただし方向は「新が速い」で、
**理論値 1.28 倍（= 0.78）には届かないが、0.95 というのは
「iq3_xxs が 55% を占め、それが 1.86 倍になった」という予測

**この乖離の理由は分かっていない。** 候補:

2. **`iq3_xxs` の 1.86 倍はカーネル単体の値**で、実際の op には DMA や量子化の
   オーバーヘッドが乗る。
3. **1 組では run 間ばらつき（27%）を分離できない。**

**§3.4 で組数を増やして再挑戦する。**

**判定: PASS（ただし効果は予測より小さい）。**

- **prefill は 5/5 の組で新が速く、中央値 4.8% 短縮。** 符号が揃っており、

1. **prefill の wall time には CPU 側の担当分が含まれる。** §4.9 の「MUL_MAT 98.9%」は
   **HTP 側の時間**の話。`override-l57.txt` で 85 テンソルが CPU に固定されており、
   **CPU 側の prefill は 1 ビットも速くなっていない。** したがって全体の短縮は
   HTP 分の短縮より小さくなる。**これが最も筋が通る。**
2. カーネル単体の 1.86 倍には DMA・量子化のオーバーヘッドが含まれていない。
3. 5 組でも run 間ばらつき（27%）を完全には分離できていない。

**「4.8% は小さい」と正直に書く。** ただし **5/5 で符号が揃った**ことは、
ゼロでない効果があることの証拠にはなる。
