## §2 目標2: `iq3_s` の 32x2 共有化 — 単体テスト（先に実施）

Phase 53 では `iq3_s` の共有化を実機に入れて hash が変わり、撤回した。Phase 54 の指示は
**「まず単体テストで 1 行版 2 回と同一の出力を確認してから実機に入れる」**なので、
その順序で進めた。

### §2.1 何を確かめるか

Phase 53 の失敗は「共有化という変換が数学的に正しいか」と「DSP 実装がその変換を
正しく実現できているか」の**2 つを分離できていなかった**ことが問題だった。
単体テストは前者だけを切り出す。

`continuations/c54/iq3s_share_check.c` を書いた:

- `ref_32x1`: `tiled_vec_dot_iq3_s_scalar_32x1`（`hvx-mm-kernels-tiled.h:1361`）の
  構造をそのまま写した参照実装
- `shared_32x2`: 重み側（qh バイト・scale バイト・fp16 の d・符号バイト・グリッド index）を
  `(kt, row)` ごとに 1 回だけ計算し、2 本の活性に使う形
- 同じランダムタイル・同じ活性・同じグリッドを与えて、行ごとに比較

**注意:** x86 には `__fp16` が無いので、IEEE half を手で decode/encode している
（`half_to_float` / `store_half`）。DSP は `__fp16` をネイティブに使うが、
**このテストで見たいのは変換の同値性であって half の丸めではない**ので、これで足りる。

### §2.2 結果

```
$ clang -O2 -o iq3s_share_check.exe iq3s_share_check.c
$ ./iq3s_share_check.exe 200
trials 200 rows_per_trial 32
mismatched rows 0
worst abs diff 0
IDENTICAL
```

**200 試行 × 32 行 = 6,400 行で、1 行も差が出なかった。最大絶対差 0。**

**したがって「共有化という変換」は数学的に正しい。** Phase 53 で実機の hash が変わったのは、
**変換そのものではなく DSP 実装（HVX のレジスタ割り当て・`restrict`・scratch の別名・
コンパイラ差）に原因がある**ことになる。

### §2.3 この結果の意味（重要）

Phase 53 の §4.10(e) に書いた候補のうち、**「変換が間違っている」可能性は消えた。**
残る候補は:

1. `iq3_s_finish_group` が `scratch` を読み、`iq3_xxs` と違って `aux` ではなく `tile` を
   渡す。**共有化で `scratch` の寿命が変わる可能性がある。**
2. `iq3_s_scale_vector` が `tile` から `hvx_vmemu` で読む。**`tile` の読み出し位置が
   2 行で共有されると、HVX のロード順序が変わる可能性がある。**
3. `valid_rows` の扱い。

**いずれも「DSP 実装の詳細」であって、アルゴリズムではない。** 単体テストでは再現しない種類の
問題なので、**実機で切り分けるしかない。**

### §2.4 次の手順（実機）

単体テストが通ったので、指示の条件は満たした。実機に入れて 32-step hash を確認する。
ただし**目標1 の A/B が走っている間は skel を入れ替えられない**ので、A/B の完了後に実施する。

### §2.5 実機での再挑戦（3 通り試して、すべて同じ hash で失敗）

単体テストが通ったので、指示の条件を満たしたうえで実機に入れた。**3 通りの実装を試し、
すべて同じ誤った hash `3b1892bf...` を出した。**

| 版 | 実装の形 | skel sha256 | 32-step hash | 判定 |
| --- | --- | --- | --- | --- |
| A | 2 行を**交互**に積算（`dot0`/`dot1` を同じ `l` ループで） | `f6077cc43fce8343f63fd4c43481039907e7d23176870363106961b2bc927c3e` | `3b1892bf...` | **不一致** |
| B | 2 行を**別パス**で積算（gather は共有、finish は行ごと） | `3a9ae5e8c7f00ad1e08d4e04e8134e3b9e60cadab875fa61e6d28b4769a3d3fd` | `3b1892bf...` | **不一致** |
| C | B から `scratch` の `restrict` を外した | `3a9ae5e8...`（**B と同一バイナリ**） | （B と同じ） | 変更なし |

**A と B が同じ hash を出したことが決定的である。** 積算の順序を変えても結果が変わらない
ということは、**「2 行を 1 回の gather で賄う」こと自体が結果を変えている。**

**C が B と同一バイナリだった**ので、`restrict` は原因ではない（コンパイラが無視した）。

### §2.6 何が起きていると考えられるか（**未解決**）

単体テストでは変換が厳密に一致するのに、実機では一致しない。**この食い違いを説明できていない。**

候補を並べる:

1. **gather の結果が行をまたいで再利用できない。** `Q6_vgather_ARMVw` の結果が
   `scratch` に書かれ、その後の `iq3_s_finish_group` が読む。**1 行目を処理した後、
   2 行目のために `scratch` を読み直すと、値が変わっている可能性がある。**
   単体テストはスカラなので gather をモデル化しておらず、**この経路を検証していない。**
2. **`iq3_s_finish_group` が `tile` から符号を読む。** `iq3_xxs` は `aux`（事前に
   `hvx_vmemu` した値）を渡すが、`iq3_s` は `tile` を渡して毎回 `hvx_vmemu` する。
   **共有すると `tile` のロードが 1 回減り、HVX のパイプラインが変わる可能性がある。**
3. **`valid_rows` の端数処理。** `hvx_vec_store_u(s, valid_rows * sizeof(float), sum)` は
   両方同じだが、`iq3_s` のほうが `valid_rows` に敏感な経路を持っている可能性。

**いずれも推測である。** 特定するには、**DSP 上で 1 行版と 2 行版の生の出力を
直接比較する**（同じタイル・同じ活性を与えて、`s0`/`s1` の float をダンプする）しかない。
`test-backend-ops` の IQ3_S 経路で M=2 と M=1×2 を比べるのが最短だろう。

### §2.7 結論と、ソースの状態

**`iq3_s` の共有化は 3 通り試して 3 通りとも失敗したので、撤回した。**
ソースは 1 行版 2 回呼びの形に戻してあり、**そのビルドが `ab407f84...`（`iq3_xxs` のみ
共有化した、32-step hash が既知値と一致する版）とバイト単位で一致することを確認した。**

```
$ cmake --build build/p53-android --target htp-v81
$ sha256sum .../libggml-htp-v81.so
ab407f84c27a0e062cc14138e6af978cd8b94f52dbab29b7fecc56b0328d36ff
```

**目標2 の判定: PARTIAL。** 単体テストは PASS（変換は厳密）。実機は **FAIL（3 通りとも
hash 不一致）**、原因は**未特定**。`iq3_s` は HTP 時間の約 22% なので、
**ここを取れないと全体の短縮は 1.45 倍には届かない。**

### §3.2 なぜ 1 組しか使えないのか（正直な原因）

**端末が 16:16 に再起動したため、このセッションは「冷えた状態」から始まった。**
Phase 53 の §9.5 で見つけた「最下段 `1113600` は 20 分以上動かない」という性質は、
**一度最下段まで加熱した後**の話であって、冷えた状態から始めると
`3628800 → 1785600 → 1670400 → 1555200 → …` と**段階的に降りていく**。
1 run が 5〜7 分かかるので、**1 組（2 run）の間に cap が動いてしまう。**

`p54_ab.sh` は最初に最下段まで待つループを入れたが、**600 秒待っても
`1113600` に到達せず**（冷えていたので）、そのまま測定に入った。これが失敗の原因である。

### §3.3 組 3 の結果（唯一の制御された比較）

| --- | --- | --- | --- |
| cap0 | 1670400（安定） | 1670400（安定） | 同一 |

| prefill 256 token | 184,128.0 ms | 183,206.5 ms | 0.995（0.5% 短縮） |
| decode | 925.6 ms | 907.6 ms | 0.981（1.9% 短縮） |
| pf/dec | 105.4 | 102.1 | 0.969 |

**1 組だけなので結論にはしない。** ただし方向は「新が速い」で、
**理論値 1.28 倍（= 0.78）には届かないが、0.95 というのは
「iq3_xxs が 55% を占め、それが 1.86 倍になった」という予測
（1/(0.45+0.55/1.86) = 1.24 倍 = 0.81）より小さい。**

**この乖離の理由は分かっていない。** 候補:

1. **prefill の律速が MUL_MAT だけではない。** §4.9 で「MUL_MAT が 98.9%」と書いたが、

2. **`iq3_xxs` の 1.86 倍はカーネル単体の値**で、実際の op には DMA や量子化の
   オーバーヘッドが乗る。
3. **1 組では run 間ばらつき（27%）を分離できない。**

**§3.4 で組数を増やして再挑戦する。**

| 中央値 | 0.973（2.7% 短縮） |
| 範囲 | 0.943 〜 1.216 |
| 新が速い組 | 3/4 |

**組 4 の decode 1,532.8 ms は外れ値として除外した。** 同じ run の prefill は 80,673 ms で
他の new の run（80,237〜82,434 ms）と同水準なので、**カーネルの効果ではなく
単発の干渉**（同時刻に私が adb で状態確認を行っていた）と判断する。**除外した事実は明記する。**

### §3.6 判定と、予測との乖離

**判定: PASS（ただし効果は予測より小さい）。**

- **prefill は 5/5 の組で新が速く、中央値 4.8% 短縮。** 符号が揃っており、
  順序（ABBA）も交互なので熱ドリフトでは説明できない。
- **しかし予測（25.4% 短縮）には遠く及ばない。**

予測の根拠: `iq3_xxs` が HTP 時間の約 55%、カーネルが 1.86 倍 →
新/旧 = 0.45 + 0.55/1.86 = **0.746（25.4% 短縮）**。
実測は **0.952（4.8% 短縮）**。

**この乖離の説明（推測、検証していない）:**

1. **prefill の wall time には CPU 側の担当分が含まれる。** §4.9 の「MUL_MAT 98.9%」は
   **HTP 側の時間**の話。`override-l57.txt` で 85 テンソルが CPU に固定されており、
   **CPU 側の prefill は 1 ビットも速くなっていない。** したがって全体の短縮は
   HTP 分の短縮より小さくなる。**これが最も筋が通る。**
2. カーネル単体の 1.86 倍には DMA・量子化のオーバーヘッドが含まれていない。
3. 5 組でも run 間ばらつき（27%）を完全には分離できていない。

**「4.8% は小さい」と正直に書く。** ただし **5/5 で符号が揃った**ことは、
ゼロでない効果があることの証拠にはなる。

### §3.7 目標1 の判定

**PASS。** 5 組の同一 cap 比較で、`iq3_xxs` 共有化は **prefill を中央値 4.8% 短縮**した
（5/5 で新が速い）。**予測の 25.4% には届かず、その理由は CPU 側が変わっていないことだと
考えられるが、分離できていない。**

### §6.3 引き継ぎ（Phase 55 へ）

#### 分かったこと

1. **`iq3_xxs` の共有化は効く。** 同一 cap 5 組で prefill 4.8% 短縮、5/5 で符号一致。
   ただし予測（25.4%）には届かない。**CPU 側が変わっていないことが主因と推測。**
2. **`iq3_s` の共有化は、変換が正しいのに実機で数値が変わる。** 3 通り試して同じ hash。
   **「gather の結果を 2 行で共有すること自体」が原因**と見られる。
3. **端末は利用者によって再起動された。** 以後の測定は「冷えた状態から cap が
   段階的に降りる」条件で行う必要がある。**Phase 53 §9.5 の「最下段は動かない」は
   一度加熱した後の性質**であり、冷えた状態には当てはまらない。

#### 次の一手（優先順）

1. **`iq3_s` がなぜ変わるのかを DSP 上で直接調べる。** 同じタイル・同じ活性で
   1 行版と 2 行版の `s0`/`s1` を float でダンプし、どこで差が出るかを見る。
   `test-backend-ops` の IQ3_S 経路で M=2 と M=1×2 を比べるのが最短。
   **これが解けないと `32x4`/`32x8` も同じ罠を踏む。**
2. **CPU 側の寄与を分離する。** `iq3_xxs` の 4.8% が予測 25.4% に届かない理由を確かめる。
   `override-l57.txt` で CPU に固定している 85 テンソルを減らせば、
   HTP 側の改善が全体に出やすくなるはず。**ただし §7.6.1 の FastRPC 停止と隣り合わせ。**
3. **`-ngl 3` と `-ngl 4` の差分**で FastRPC が返らなくなるテンソルを絞る（Phase 53 の続き）。
4. 目標3・5 の未実施項目。
