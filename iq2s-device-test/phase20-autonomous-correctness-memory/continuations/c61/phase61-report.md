### §0.4 重大な発見: 基準バイナリは tiled が完全にコンパイルアウトされている

指示の目標0-4「c60-neon + `GGML_CPU_TILED_MM=0` でも `e9da92f8` が一致することの裏取り」
を実行したところ、**一致しなかった**（`c7564354af84c751912a665853df42e484edf7aea9f40a8016df17bec19a2f6a`）。

原因を追い込んだ結果、**基準 `0a3db9c5` は `ggml_compute_forward_mul_mat_tiled` が
`mov w0, wzr; ret`（常に false）にコンパイルされている**ことが分かった:

```
$ llvm-objdump -d build/p52/devlibs/libggml-cpu.so --start-address=0x59e20
0000000000059e20 <ggml_compute_forward_mul_mat_tiled>:
   59e20:  mov  w0, wzr
   59e24:  ret
```

これは Phase 60 で ARM gate を開放する**前**のソース（`__ARM_NEON` が gate 条件に入って
いない版）でビルドされているため。つまり:

- **基準 `0a3db9c5` では tiled は絶対に走らない。** `e9da92f8` は純粋な stock パスの hash。
- Phase 60 以降のビルドは gate が入っているので、`GGML_CPU_TILED_MM=0` でも
  `ggml_tiled_wdata_size()` が 0 以外を返しうる（`ggml_tiled_supported` が型を見るため）。

### §0.5 なぜ hash が変わるのか（機構）

`ggml-cpu.c:1605` で tiled の作業バッファは `params->wdata` から取られる:

```c
char * tiled_scratch = incr_ptr_aligned(&wdata_cur, ggml_tiled_wdata_size(nth, dst), 64);
```

`ggml_tiled_wdata_size()` は `ggml_tiled_supported()` が真なら
`64 + n_tasks * 512KB` を返す。**この予約が 0 か非 0 かで、後続の全バッファの
オフセットがずれる。** オフセットがずれるとキャッシュライン境界が変わり、
スレッドの分割と浮動小数の加算順序が変わって hash が変わる。

**したがって「tiled を OFF にすれば基準と同じ hash」は成立しない。**
Phase 60 の報告書 §2.4.3 が FORCE 経路で品質ゲートを取ったのは正しかったが、
「`GGML_CPU_TILED_MM=0` で `44cd99ce` に戻る」という前提は**この fork では誤り**だった。

### §0.6 切り分けの記録（すべて実測、すべて `c7564354`）

| 仮説 | 検証 | 結果 |
| --- | --- | --- |
| dotprod が原因 | `c60scalar`（armv8-a、`sdot` 0 個）+ tiled OFF | `c7564354` → **否定** |
| OpenMP が原因 | `c61-neon`/`c61-scalar` を `GGML_OPENMP=ON` でビルド | `c7564354` → **否定** |
| `-march` が原因 | `c61-noarch`（`GGML_CPU_ARM_ARCH` 空、`-march` なし） | `c7564354` → **否定** |
| ARM gate が原因 | gate を Phase 60 前の形に戻してビルド（`c61-nogate`） | `c7564354` → **否定** |
| 基準バイナリ自体 | `0a3db9c5` を再実行 | `e9da92f8` → **環境は正常** |

**結論: 差は「tiled のコードがバイナリに入っているかどうか」そのもの。**
gate を戻しても消えないのは、`ggml_tiled_wdata_size` の呼び出しが
`ggml-cpu.c` に残っており、`ggml_tiled_supported` が型を見て真を返すため。

### §0.6.1 ライブラリの組み合わせでも hash が変わる（追加の実測）

端末の `libggml-base.so` は `d950aa96`（7,802,768 B、エクスポート 1,384 シンボル）で、
**現在のソースツリーからビルドしたもの（8,250,736 B、1,536 シンボル）とは別物**である。
端末のものは libomp に依存せず（`NEEDED` に無い）、Phase 52 頃のビルドと推定される。

そこで **base と cpu を揃えた組**（`build/c61m-neon`、両方 `GGML_OPENMP=OFF`）を
端末に入れて測った:

| 組 | cpu | base | NGL=44 の hash |
| --- | --- | --- | --- |
| 基準 | `0a3db9c5` | `d950aa96` | `e9da92f8` |
| 揃えた組 | `17afd925` | `a410309a` | `c829c6ea` |
| 混成（c60-neon + 端末 base） | `318508e8` | `d950aa96` | `c7564354` |

**3 組とも違う hash になる。** つまり hash は「どのバイナリの組み合わせか」に依存する。
これは異常ではなく、`wdata` レイアウトとスレッド分割が変われば浮動小数の加算順序が
変わるという当然の帰結である。

**したがって A/B は「基準バイナリ（`0a3db9c5` + `d950aa96`）vs 新バイナリ」で取る。**
新バイナリ側は端末の base と依存が合っている必要がある。`c60neon2`（`318508e8`）は
`GGML_OPENMP=OFF` ビルドで libomp に依存しないため、端末の base と整合する。
**これが目標1の A/B に使う組である。**

### §0.7 この発見の意味

1. **Phase 60 の「`GGML_CPU_TILED_MM=0` で `44cd99ce` に戻る」という記述は誤り。**
   Phase 60 報告書 §1.3 の表で「tiled-on と tiled-off が同一ハッシュ `ede05813`」と
   書いたのは、**両方とも tiled パスに入っていなかった**（1 token < 8 行）ため。
   あの比較は「tiled が効いていない」ことの証拠にはなるが、「OFF で基準に戻る」ことの
   証拠にはならない。
2. **今後の A/B は「基準バイナリ vs 新バイナリ」で取るしかない。** 同一バイナリ内の
   env 切り替えでは、wdata レイアウトが同じなので比較には使える（tiled ON vs OFF は
   同じバイナリなので wdata サイズは同じ）。**ただし基準 hash とは一致しない。**
3. **既定 ON の判断（目標2）はこの影響を受ける。** 既定 ON にすると
   `e9da92f8` は二度と出なくなる。これは「退行」ではなく「tiled が入ったことによる
   正当な変化」だが、**回帰ゲートの基準を取り直す必要がある。**

### §1.5 壁の内訳（cpu_split_us の意味）

**グラフ全体のうち CPU バックエンドが担当した部分の時間**である。

| 条件 | A base | B neon | 削減 |
| --- | --- | --- | --- |
| nt=128, cap 1,670,400 | 11,105,659 us | 7,744,084 us | **-30%** |

| nt=512, cap 1,670,400 | 10,413,578 us | 4,295,109 us | **-59%** |
| nt=512, cap 1,555,200 | 10,718,113 us | 7,511,056 us | **-30%** |

**CPU 床は確かに下がっている。** ただし wall の改善（1.6-1.8 倍）は CPU の削減率より
小さい。これは **wall の主体が CPU から HTP 側に移った**ことを意味する。

Phase 58 の見積もり（CPU 1 層 1.34 s、HTP 層 0.6-0.85 s）に今回の数字を当てると:

- NGL=44 は CPU 21 層 + HTP 43 層。
- CPU 床が 30-59% 下がったので、CPU 側は約 28 s -> 約 15 s（128 token 換算）。
- HTP 側は変わらないので、wall は「HTP 律速」に近づく。

**これが目標1b（NGL 再探索）の動機である。** CPU 床が下がったのなら、
CPU 層をもっと HTP に渡す（NGL を上げる）方が有利になる可能性がある。

## §2 目標1b: NGL 再探索（tiled ON）- **PASS（既定 44 が最良のまま）**

### §2.1 掃引

構成: skel `76dd89e3` + cpu `318508e8` + `GGML_CPU_TILED_MM=1`、prefill 128、同一セッション。
cap は 1,670,400 でほぼ安定（ngl16 だけ開始時 1,785,600）。

| 32 | 34,308.29 | 964.64 | 8,613,506 | |
| 40 | 34,662.09 | 929.78 | 7,668,821 | |
| **44** | **30,352.42** | 1,716.38 | 6,243,093 | **prefill 最良**、decode は外れ値 |
| 48 | 30,814.41 | 880.74 | 5,470,850 | prefill 2 位 |
| 50 | 32,109.40 | 899.18 | 5,237,831 | |
| 56 | 34,819.57 | 1,131.15 | 3,036,337 | |

### §2.2 判定: **NGL=44 が最良のまま。既定を変える理由はない。**

- prefill は **44 と 48 がほぼ同等**（30.35 s vs 30.81 s、差 1.5%）。
- 50 は 32.11 s で 5.8% 遅い。**Phase 58 で NGL=50 が最良だった結果は再現しない。**
- 56 は 34.82 s で明確に遅い。
- decode は 44 の 1,716 ms が外れ値（他は 880-1,180 ms）。**再測が必要**（目標4 で取る）。

### §2.3 プラトーの確認（指示の見込みは当たったか）

指示には「CPU 床が約 0.63 s/層まで下がると HTP 層と同程度になり、wall が NGL に対して
平坦になる（プラトー）可能性がある」とあった。

**実測はプラトーではなく、浅い谷だった。** NGL 32-56 の範囲で prefill は
30.35-34.82 s、つまり **±7% の範囲に収まっている**。Phase 58 の測定
（44: 54.92 s、50: 49.66 s、56: 49.02 s）では 44 と 56 で 11% の差があったが、
今回は 44 と 56 で 15% の差がある（44 が良い方向）。

**解釈**: CPU 床が下がったことで、**最適点が低 NGL 側に戻った**。
Phase 58 では CPU が重いので NGL を上げる（CPU 層を減らす）方が有利だった。
今回は CPU が軽いので、NGL を上げると HTP の負担増（と HTP 側の非効率）が
上回るようになった。**これは tiled が効いたことの間接的な証拠である。**

### §2.4 cpu_split_us の単調減少

`cpu_split_us` は NGL に対して単調に減る（18.5M -> 3.0M）。これは
「CPU 層の数」に比例しており、想定どおり。**wall が減らないのは HTP 側が増えるから。**

### §5.3 なぜ条件2 が原理的に満たせないか

§0.4-0.5 で特定したとおり、`ggml_tiled_wdata_size()` が `params->wdata` から
`64 + nth * 512KB` を予約するかどうかで、後続バッファのオフセットが変わる。
`ggml_tiled_supported()` は `GGML_CPU_TILED_MM` ではなく**型と arch** を見るので、
**既定を OFF にしても予約は発生する**（Phase 60 の gate 変更が入った時点で確定）。

つまり「既定 ON にすると hash が変わる」のではなく、
**「Phase 60 で gate を ARM に開放した時点で hash は変わっていた」**。
既定 ON/OFF は無関係である。

**したがって条件2 は「既定 ON のせいで満たせない」のではなく、
「gate 開放そのものが hash を変える」ので、既定 ON の可否とは独立に満たせない。**

### §5.4 見送りの内容と、代わりに何をすべきか

**既定 ON は見送る。** `ggml_tiled_matmul_enabled()` の ARM 既定は `false` のまま
（ソースは変更していない。実験用ビルドだけを `ddb07e63` として作った）。

代わりに、**運用で `GGML_CPU_TILED_MM=1` を明示的に渡す**ことを推奨する:

- 速度は 2.14 倍（prefill 128）、1.71 倍（prefill 512、NGL=44）。
- 品質は argmax 4/4、top-5 4/4、スケール比 2.4% 以内。
- **replay hash は変わる**ので、回帰ゲートを使うときは `GGML_CPU_TILED_MM=0` を
  明示的に渡し、かつ**基準バイナリ（`0a3db9c5`）を使う**必要がある。

**既定 ON を将来やるなら、先に回帰ゲートの基準を取り直す必要がある。**
これは Phase 62 の課題として記録する。

### §6.1 上流 NEON 実装（重要）

[hardwiredagent/silicon-forge-arm-neon-study](https://github.com/hardwiredagent/silicon-forge-arm-neon-study)
（MIT、2026-11-11）のカーネルを読んだ。**本 fork の実装とは設計が違う**:

| 側面 | 上流 study | 本 fork |
| --- | --- | --- |
| src1 レイアウト | **その場で interleave**（`tiled_repack_src1` が実装） | 自然レイアウト（no-op） |
| dot 命令 | `vdotq_laneq_s32`（レーン指定） | `vdotq_s32` |
| タイル形状 | 4 src0 行 x 16 src1 行 | 1 src0 行 x 16 src1 行 |
| アキュムレータ | `float32x4_t acc[16][4]` = 64 レジスタ | `int32x4_t acc[16]` = 16 レジスタ |
| 縮約 | **なし**（レーン = 行） | `vaddvq_s32` で水平加算 |

**6.5 倍（Neoverse N1）と 2.14 倍（8 Elite Gen 5）のギャップ**は 3 要因に分解できる:
1. **ベースラインが違う**（study は IQ3_M 単体、本 fork は 27B 全体で CPU 層は 21/64）
2. **SoC が違う**（サーバ向け vs スマホ、熱制限）
3. **カーネルが違う**（interleave により水平縮約が消える）

**1 と 2 が主因**と判断する。3 も実在するが、study 自身が「Arm の数字は x86 より
まだかなり低い。何が上限かはプロファイルしていない」と書いている。

**取り込みは禁止なので、候補のリスト化だけした**（`p61_upstream_neon_analysis.md` §4）。
最有力は「interleave + `vdotq_laneq_s32` + 4x16 タイル」だが、
`tiled_repack_src1` の実装が必要で影響範囲が広い。Phase 62 の候補。

### §8.2 分かったこと（要約）

1. **tiled の end-to-end 効果は prefill 128 で 1.60 倍、512 で 1.71 倍（中央値）。**
   Phase 60 の CPU 単体 2.14 倍から減衰するが、NGL=44 では CPU 層が 21/64 しかないので
   想定内。**バッチが大きいほど効果が大きい**という予想も当たった。
2. **基準バイナリ `0a3db9c5` は tiled が完全にコンパイルアウトされている。**
   `ggml_compute_forward_mul_mat_tiled` が `mov w0, wzr; ret`。
   **これが「tiled OFF で基準 hash に戻る」を不可能にしている**（§0.4-0.5）。
3. **hash はバイナリの組み合わせ全体に依存する。** 基準 / 揃えた組 / 混成で 3 つとも違う。
   `wdata` レイアウトが変わればスレッド分割と浮動小数の加算順序が変わるため（§0.6.1）。
4. **NGL=44 が最良のまま。** Phase 58 の「NGL=50 が最良」は再現しない。
   **CPU 床が下がったことで最適点が低 NGL 側に戻った**と解釈できる（§2.3）。
5. **Phase 59 の「NGL=50 は decode が 1.5-1.9 倍遅い」は分散だった。**
   6 run の中央値では NGL=50 の方が 5.7% 速い。IQR が中央値の 11-12% あり、
   少ないサンプルでは区別できなかった（§4.3）。
6. **既定 ON は見送り。** 速度・品質は条件を満たすが、replay hash 不変の条件が
   原理的に満たせない（gate 開放そのものが hash を変える）。運用で
   `GGML_CPU_TILED_MM=1` を明示する方針を推奨（§5.4）。
7. **上流の NEON 実装は設計が違う。** interleave + `vdotq_laneq_s32` + 4x16 タイルで

8. **上流 61 コミットのうち 50 件が welcome。** `ggml-cpu/tiled` には 0 件なので
   Phase 60 の作業とは衝突しない（§6.3）。
