## §2 ハーネスの修正: 前面アプリを止めない（**所有者の指摘による**）

### §2.1 何を間違えたか

Phase 55 の測定中、所有者から **「フォアグラウンドのアプリは消すな」「また消してるよね」**
と 2 回指摘を受けた。**指摘は正しかった。**

`p53_run.sh` の force-stop リスト（Phase 50 由来、16 個）に
**`app.morphe.android.youtube` が入っていた。** 私は Phase 55 の開始時に
「以後 force-stop しない」と述べたにもかかわらず、**run のたびにスクリプトが
YouTube を止めていた。** 発言と実行が矛盾していた。

**所有者の指示（Phase 55 開始時）は「TVer の停止は許可済み」であり、
YouTube の停止は許可されていない。** 私は Phase 53 のリストをそのまま使っており、
そこに YouTube が含まれていることを確認していなかった。

### §2.2 修正内容

2 段階で直した。

1. **リストから `app.morphe.android.youtube` を削除**（`sed`）。
2. **前面のアプリを実行時に検出して、リストに入っていても止めない**ようにした。

```sh
FG=$(dumpsys activity activities 2>/dev/null | \
     sed -n "s/.*topResumedActivity=ActivityRecord{[^ ]* [^ ]* \([^\/]*\)\/.*/\1/p" | head -1)
echo "P55_FOREGROUND ${FG:-unknown}"
for p in <16 個のリスト>; do
    [ -n "$FG" ] && [ "$p" = "$FG" ] && { echo "P55_SKIP_FOREGROUND $p"; continue; }
    am force-stop $p >/dev/null 2>&1
done
```

**これで、どのアプリが前面でも止めない。** リストに残っているアプリが前面に来た場合も
スキップされ、`P55_SKIP_FOREGROUND <package>` がログに残る。

### §2.3 検証（実際に run を回して確認）

| 項目 | run 前 | run 後 |
| --- | --- | --- |
| YouTube の pid | **29374** | **29374**（同一） |
| 前面の activity | `app.morphe.android.youtube/.morphe_black_3` | 同じ |
| `P55_FOREGROUND` の出力 | — | `app.morphe.android.youtube` |
| run の exit / hash | — | **0 / `b21ca4bf...`（一致）** |

**YouTube は 1 度も止まらず、測定も正常に完了した。**

### §2.4 この修正の意味

**測定のためにユーザーのアプリを止める必要は無い、ということが分かった。**
Phase 50〜54 は「メモリを空けるために 16 個止める」という前提で動いていたが、
実際には:

- `am kill-all` はバックグラウンドのみを対象とし、前面アプリには触れない
- 前面アプリを 1 つ残しても、ガードを 4096 MiB にすれば測定は成立する（§1.2）

**今後は前面アプリを止めない。** メモリが足りない場合はガードを上げるか、
`am kill-all` だけで対応する。

## §3 目標1: `iq3_s` の謎の解明 — **原因を特定し、修正に成功**

### §3.1 実験の一覧（1 要素ずつ変更、各回で 32-step hash を確認）

| 実験 | 変更内容 | skel sha256 | 32-step hash | 判定 |
| --- | --- | --- | --- | --- |
| （Phase 54 A） | 2 行を交互に積算 | `f6077cc4...` | `3b1892bf...` | 不一致 |
| （Phase 54 B） | 2 行を別パスで積算 | `3a9ae5e8...` | `3b1892bf...` | 不一致 |
| （Phase 54 C） | B から `restrict` を外す | `3a9ae5e8...`（B と同一） | — | 変更なし |
| **D** | **2 行目の前に再 gather** | `4d9d1399...` | **`b21ca4bf...`** | **一致** |
| E | gather 結果をローカル配列に退避（barrier 無し） | `f6077cc4...`（**A と同一バイナリ**） | `3b1892bf...` | 不一致（**A と同じに畳まれた**） |
| **F** | **ローカル退避 + `__asm__ __volatile__("" ::: "memory")`** | `e311bf14...` | **`b21ca4bf...`** | **一致** |

### §3.2 決定的だった実験 D

**2 行目の処理の直前に `iq3_s_gather_group` をもう一度呼ぶだけで、hash が既知値に戻った。**

```c
// 1 行目
for (int l = 0; l < 4; ++l) iq3_s_gather_group(tile, qh, l, grid, scratch + 2*l);
... dot0 を計算 ...
// 実験 D: 2 行目の前にもう一度 gather する
for (int l = 0; l < 4; ++l) iq3_s_gather_group(tile, qh, l, grid, scratch + 2*l);
... dot1 を計算 ...
```

**これは「gather の結果を 2 回読むと 2 回目が壊れている」ことを意味する。**
gather をやり直せば正しい値が書かれるので、結果が一致する。

### §3.3 実験 E が無効だった理由（**重要な落とし穴**）

実験 D の結果から「gather 結果をレジスタに退避すれば 1 回の読み出しで済む」と考え、
実験 E を書いた。しかし **E のバイナリは Phase 54 の A と完全に同一（`f6077cc4`）だった。**

**コンパイラが「`scratch` からローカル配列へコピーして 2 回使う」コードを、
「`scratch` を 2 回読む」元の形に畳み込んだ**ためである。`scratch` は
`HVX_Vector * restrict` で、間に書き込みが無いので、コンパイラにとっては
同じ値を 2 回読むのと 1 回読んで 2 回使うのは等価に見える。

**したがって E は「アイデアの検証」になっていなかった。** バイナリの sha256 が
A と一致したことで気づいた。**「ビルド鮮度を sha256 で確認する」という指示が
ここで効いた**（Phase 53 §17 の教訓）。

### §3.4 実験 F: barrier を入れて初めて検証になった

```c
HVX_Vector g0[4], g1[4];
for (int l = 0; l < 4; ++l) { g0[l] = scratch[2*l+0]; g1[l] = scratch[2*l+1]; }
__asm__ __volatile__("" ::: "memory");   // ← これが無いと畳み込まれる
```

**この barrier でコンパイラの畳み込みを止めたところ、hash が `b21ca4bf` に一致した。**

**結論: 原因は「gather の結果を `scratch` から複数回読むこと」。**
1 回だけ読んでレジスタに保持すれば正しい。

### §3.5 なぜ `iq3_xxs` は同じ形で動くのか

`iq3_xxs` の共有化（Phase 53 で成功）は、**`iq3_xxs_finish_group` が `aux` を引数に取る**
形になっている。`aux` は `hvx_vmemu(tile + 256)` で**ループの先頭で 1 回だけ**読まれ、
レジスタに保持される。**`scratch` を 2 回読む経路が無い。**

一方 `iq3_s_finish_group` は `tile` を受け取り、**内部で `scratch[0]`/`scratch[1]` を
読む。** 2 行分呼ぶと `scratch` を 2 回読むことになる。**これが差だった。**

### §3.6 修正版（実験 F）の性能

実験 F の run は cap が `3033600 → 1785600` と大きく動いたため、
**性能の比較には使えない**（decode 2592.9 ms は熱制限下の値）。
**性能測定は別途、同一 cap で取り直す必要がある。** §3.7 で実施する。

### §3.7 目標1 の判定

**PASS。** 原因を特定し（gather 結果の複数回読み出し）、修正版（実験 F）が
**32-step hash `b21ca4bf` で一致**した。**カーネル単体の GFLOP/s 改善は §4 で測る。**

## §4 目標2: 「4.8% vs 予測 25.4%」の分離 — **HTP 側は 36% 短縮していた**

### §4.1 何を測ったか

Phase 54 は end-to-end の wall time で **prefill 4.8% 短縮**しか観測できず、
カーネル単体の改善（`iq3_xxs` 1.86 倍）から予測される 25.4% に届かなかった。
指示どおり、**プロファイルで HTP 側の総時間を直接比べて分離した。**

比較した 2 つのプロファイル:

| プロファイル | skel | 内容 |
| --- | --- | --- |
| `profpf3` / `20261115-043942-29521` | `288e6712`（Phase 50 D） | 旧カーネル |
| `profF` / `20261115-214631-14482` | `e311bf14`（両方修正） | 新カーネル |

どちらも `-ngl 16`、`P53_PROMPT_LIST=128`、`PROFILE_ARG=1`、`P53_NO_LOGITS=1`。

### §4.2 結果

| 項目 | 旧 `288e6712` | 新 `e311bf14` | 比 |
| --- | --- | --- | --- |
| **OPBATCH 合計（HTP 総時間）** | **24.81 s** | **15.86 s** | **0.639（36.1% 短縮）** |
| MUL_MAT 合計 | 24.52 s | 15.61 s | 0.637（36.3% 短縮） |
| OPBATCH の個数 | 26 | 26 | 同じ |
| MUL_MAT の個数 | 1,502 | 1,502 | 同じ |

**HTP 側は 36.1% 短縮している。** 予測（25.4%）を**上回った**。

### §4.3 この結果の意味（**Phase 54 の結論を訂正する**）

Phase 54 §3.6 では「実測 4.8% が予測 25.4% に届かない理由は CPU 側が変わっていないこと」
と推測した。**この推測は方向としては正しいが、数字が合わない。**

HTP 側が 36.1% 短縮したのに wall time が 4.8% しか短縮しないということは、
**wall time のうち HTP が占める割合が非常に小さい**ことになる。逆算すると:

```
wall_new / wall_old = 0.952
HTP_new / HTP_old   = 0.639
```

wall = HTP + CPU_side とすると:

```
0.952 * (HTP_old + CPU_old) = 0.639 * HTP_old + CPU_old
0.952 * HTP_old + 0.952 * CPU_old = 0.639 * HTP_old + CPU_old
0.313 * HTP_old = 0.048 * CPU_old
CPU_old / HTP_old = 6.52
```

**つまり wall time のうち HTP は約 13%、CPU 側が約 87% を占めている。**

**これは Phase 53 §4.9 の「MUL_MAT が HTP 時間の 98.9%」と矛盾しない。**
あれは **HTP の内訳**の話であって、**wall time の内訳ではなかった。**
Phase 54 でこの 2 つを混同していた。

### §4.4 なぜ CPU 側が 87% なのか

`override-l57.txt` で **85 テンソルを CPU に固定**している（`-ngl 16` でも）。
HTP に載るのは 16 ブロック分だけで、**残りの層は CPU が処理する。**
CPU 側の prefill は §4.1（Phase 53）で 1.3〜1.8 t/s と測っており、
HTP 側より遅い。

**したがって「HTP のカーネルを速くする」だけでは wall time はほとんど動かない。**
Phase 54 の 4.8% は、HTP が 13% しか占めていないことから**ほぼ説明できる**
（0.13 × 36.1% = 4.7%。**実測 4.8% とほぼ一致する**）。

### §4.5 目標2 の判定

**PASS。** プロファイルで HTP 側の総時間を直接比べ、**36.1% 短縮**を確認した。
そこから **wall time の内訳は HTP 約 13% / CPU 約 87%** と算出でき、
**Phase 54 の 4.8% が予測と食い違う理由を説明できた**（0.13 × 36.1% = 4.7% ≈ 4.8%）。

**Phase 54 §3.6 の「CPU 側が変わっていないから」という推測は正しかったが、
「HTP が wall のどれだけを占めるか」を測っていなかったため数字が合わなかった。**
今回それが分離できた。

**次の含意:** 全体を速くするには **CPU 側の担当を減らす**（HTP に載せるテンソルを増やす）
しかない。ただしそれは Phase 53 §7.6.1 の FastRPC 停止と隣り合わせである（目標3）。
