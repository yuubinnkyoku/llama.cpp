### §4.1 失敗 1: `WANT_SKEL` ガードで B 腕が全部走っていなかった

最初の ABBA（タグ `abba`、2 ラウンド）は**全 B 腕が rc 2 で拒否されていた**:

```
REFUSING: skel sha256 76b20839... != 312ad7b7...
SPLIT_RUN rc 2 dir /data/local/tmp/c46-27b/runs/20261127-014329-10434/
```

`p53_run.sh`（内部の `run53.sh`）は**インストール済み skel が既定の `WANT_SKEL`
（`312ad7b7`）と違うと実行を拒否する**。Phase 63 で記録済みの罠だが、
スクリプト側で踏んだ。しかも私のスクリプトは `rc 2` を検出しても
**中断せず、古い run ディレクトリの数値を報告していた**ため、
出力は「全 B 腕が A-512 と完全に同じ数値」という明白な異常になった。

**対策（2 つ）**:
1. `arm()` で skel の sha256 を控え、`pf()` に `WANT_SKEL=$CUR_SKEL` を渡す。
2. `rc != 0` なら `P65A_ABORT` を出して**即中断**（古い値を報告しない）。

**この失敗データは破棄した。** 対策後に B1 腕の単発スモークテストが
84.59 s で完走することを確認してから再測定した。

| B1 | 128 | 62,519.84 | 1,113,600 |
| B1 | 512 | **162,393.54** | 1,113,600 |
| B2 | 128 | **53,478.04** | 1,113,600 |
| B2 | 512 | 171,873.73 | 1,113,600 |

**A-128 の 210,312.555389 は、ラウンド 2 の A-512 の値と完全に同一**である。
これは実測値ではなく**前の run のディレクトリを読んだもの**。

**原因**: `pf()` は
`R=$(grep -oE "SPLIT_RUN rc [0-9]+ dir .*" $BASE/p53-$T.out | awk '{print $NF}')`
で run ディレクトリを求めるが、`p53_run.sh` がログを書き終える前に読むと
grep が空になり、フォールバックの `ls -td runs/*/ | head -1` が
**直前に終わった run のディレクトリ**を返す。ラウンド先頭の run で起きやすい。

**対策（未実装・次フェーズ）**: ログの生成を待つ、または run 開始時刻より
新しいディレクトリだけを候補にする。あるいは `p53_run.sh` が stdout に
`SPLIT_RUN ... dir` を出しているので、ログ経由でなく**標準出力から直接取る**。

**同一値の重複を機械的に検出するチェックも入れるべきである**
（`prefill_ms` が既出値と一致したら警告）。今回は手で気づいた。

### §4.7 修正後の判定

**確定できること: B1 と B2 はどちらも A より速い。**

### §4.8 載せ替え判断（訂正後）: **見送り**

**退行が無いことは 3 セル x 2 cap で示せた。** 品質も両方 PASS 済み。

## §19 目標4-2: #31055（KV-head team split）- **適用外と判明（未実施ではなく不要）**

「未実施」として繰り越していたが、**この端末・この構成では原理的に発動しない**
ことを実測で確認した。**未達ではなく適用外**である。

### §19.1 #31055 が何をするか（上流のコードを読んだ）

`htp_fa_mdev_teams()` が要:

```c
// Multicore: gcd(n_kv_heads, N) teams own the KV heads, team members share the Q-blocks
const uint32_t t = (head_split && n_kv_heads > 0 && mdev_count > 1) ? hex_gcd_u32(n_kv_heads, mdev_count) : 1;
*n_teams   = t;
*team_size = mdev_count > 1 ? mdev_count / t : 1;
```

有効化条件（`htp-kparams.cpp`）:

```c
if (opt_fa_split && mdev_count > 1) {
    htp_fa_mdev_teams(n_kv_heads, mdev_count, ...);
    if (fa_team_size > 1) { kparams->flags |= HTP_FA_FLAG_TEAM_SPLIT; }
}
```

**`mdev_count > 1` が必須。** `mdev_count == 1` なら `n_teams = gcd(kv, 1) = 1`、
`team_size = 1` となり **フラグが立たない**（＝発動しない）。

### §19.2 この構成の `mdev_count` は 1

実行ログ:

```
ggml-hex: device 0: HTP0:0 (phys=0, virt=0, domain=nsp1000:1000)
```

**デバイスは 1 つだけ。** したがって **#31055 はこの 27B 構成では何もしない。**

### §19.3 2 セッションにすれば 2 デバイスになるか -> **ならない**

PrismML の hexagon preset は 4 セッション（`--device HTP0,HTP1,HTP2,HTP3`）を
使っていたので、セッションを増やせば並列化できる可能性を実測した。

`p65_mdev.sh` で `HTP0:0` と `HTP0:0,HTP0:1` を交互に 2 ラウンド:

| ラウンド | 構成 | 実際のデバイス数 | prefill 128 ms | cap |
| --- | --- | --- | --- | --- |
| 1 | `HTP0:0` | **1** | 51,812.94 | 1,670,400 |
| 1 | `HTP0:0,HTP0:1` | **1** | 48,115.37 | 1,670,400 |
| 2 | `HTP0:0,HTP0:1` | **1** | 44,944.59 | 1,670,400 |
| 2 | `HTP0:0` | **1** | 49,091.19 | 1,670,400 |

**4 run すべてで `ndev 1`。** `HTP0:1` を指定しても**デバイスは増えない**
（バックエンドが 1 つに畳んでいる）。

したがって **「2 セッションにすれば #31055 が効く」は成立しない。**

**時間の差（48.1/44.9 vs 51.8/49.1）は構成の差ではない。**
同じ実効構成（ndev 1）で、順序が 2〜3 番目の run が速く出ているだけであり、
**ウォームアップのドリフト**である。**構成比較として使ってはいけない。**

### §19.4 結論

**#31055 は本端末・本構成では適用外。取り込む価値は無い。**

- 発動条件 `mdev_count > 1` を満たせない（実測で 1）。
- セッションを増やしてもデバイス数は増えない（実測）。
- **したがって移植作業は不要。** この判断は実測に基づく。

**将来 `mdev_count > 1` が実現する場合**（複数 SoC・複数ドメイン・
将来のバックエンドが複数セッションを実デバイスとして扱う場合）に限り再評価する。

### §19.5 この節の位置づけ

**「時間が無くてできなかった」ではなく「測定した結果、不要と判明した」。**
Phase 65 の未実施項目のうち、これが最も大きな残件だったので、
適用外と確定できたことは進展である。

**副次的に、§18 で修正した replay 復元の検証が機能した**
（`p65_mdev.sh` は復元後に期待値と比較し、`P65M replay_restore OK` を出力した）。
