### §1.3 結論: **用途別プリセットは不要。NGL=44 を全用途で維持する**

**prefill も decode も NGL=44 が最良**である。
Phase 65 が想定した「prefill 重視=44 / decode 重視=0」という
**トレードオフは存在しない。**

- **decode**: 44 が 0 より 1.71 倍速い（t=-16.4、完全分離）

**したがって `run53.sh` への decode モード切替の追加は行わない。**
既定 44 のままで、両方の用途に最適である。

### §1.5 Phase 65 がなぜ違ったか - **仮説（未証明）**

**最も可能性が高い説明: Bonsai モデル（7.15 GiB）が同居していたことによる
ページキャッシュの圧迫。**

Phase 65 の終了時、端末の空きは **2.7 GB** で、9.26 GB の 27B と
7.15 GiB の Bonsai が同居していた。27B の重みがページキャッシュに
常駐できず、**decode のたびにフラッシュから読み直していた**可能性がある。

今回は 42 GB 空きで、`Cached 10.57 GB` / `MemAvailable 10.74 GB` と
**27B（9.26 GB）が丸ごとキャッシュに載っている。**

これが正しければ、Phase 65 では**HTP に重みを移す NGL=44 が最も損をした**
（HTP 用バッファとページキャッシュが競合するため）ことになり、
観測（Phase 65 で 44 だけが 3 倍近く遅い）と整合する。

**Phase 65 の prefill も同様に歪んでいた**: NGL=0 の prefill は Phase 65 で
約 91 s、今回は 37-38 s（**2.4 倍の差**）。CPU 側の重み読み出しが多い構成ほど
大きく遅くなっており、ページキャッシュ仮説と方向が一致する。

**ただし証明はしていない。** 検証するには、Bonsai を再配置するか
RAM を消費してページキャッシュを追い出した状態で同じ測定をやり直す必要がある。
**Phase 65 のログには `P53_MEM_END` が残っておらず、当時の MemAvailable を
直接確認できなかった**（ログ形式が異なる回があった）。

**確定したこと**: **空きメモリが十分な状態では NGL=44 が decode・prefill とも最良。**
**未確定**: Phase 65 の数値がページキャッシュ起因だったという説明。

### §1.6 測定品質について（重要）
